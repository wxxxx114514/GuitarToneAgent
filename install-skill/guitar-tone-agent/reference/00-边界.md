# 边界

> 这个 Skill 能做什么、不能做什么、能力上限在哪
> 从 SKILL.md 拆出。**这是参考资料，不是指令。**

---

## 0. 先读这一节：这个 Skill 的边界

**做什么**
- 从一首歌里提取吉他音色的**目标指纹**（频谱包络 / 谐波 / 动态 / 空间感）
- 在硬件效果器上通过**修改预设 JSON** → 加载 → 播放 DI → 录制湿声 → 算误差 → 搜参数
- 输出一份能用的预设

**不做什么**
- 不追求「逐样本还原」——**源差异（DI 不同 / 演奏不同）是物理上限**
- 不做软件箱模仿真，一切以**真机测量**为准
- **不做「比人耳更好」的调音**（见 §10.7）

**能力上限（物理的，说清楚免得白费功夫）**

参考录音如果是**真箱 + 麦克风实录**，那么：

```
抓得到：  箱体 + 麦克风的【频响曲线】（这就是 IR 能做的全部）
抓不到：  功放与喇叭的【阻抗交互】（随驱动电平变）
          喇叭大音量下的【非线性】（纸盆形变、压缩）
          麦克风的【近场效应】
          房间
```

**而参考录音是整条链**：`amp → cab → mic → 话放 → 后期 EQ → 压缩 → 混音`。
**中间那几截，模拟抓不到，也调不掉。**

> **所以：撞上这条上限时，正确的做法是承认它，不是继续调。** 判断方法见 §10.7。

### 0.1 ⭐ 开工前第一件事：确定【当前是哪首歌】

> **这个 Skill 是通用方法论，不绑定任何一首歌。**
> **文档里的所有数字都是历史实测记录，不是当前任务。**

**新对话开始时的固定动作（不要跳过）：**

```
① 问清楚（或从上下文确认）：当前要做哪首歌？
② 找那首歌的工作目录
③ 检查已有的产物：目标曲线？演奏规格？DI？预设？
④ 缺什么补什么（见 §9.0）
```

**⛔ 不要做的事：**
```
✗ 没确认歌名就开始测量
✗ 假设脚本知道你要处理哪首歌
```

**所有脚本都通过 `SONG_DIR` 找数据，不假设是哪首歌**（见 §2.4）。

**如果用户没说歌名，就问一句。** 一句话的成本，远低于在错的歌上跑一整套测量。

#### 每首歌一个工作目录（约定）

```
songs\<歌名>\
    source.flac          原曲
    stems\               分离结果（guitar.wav / bass.wav / ...）
    target.npy           全曲目标曲线（13 频段）
    spec.json            演奏规格（调性 / 主要和弦 / 奏法 / 音区 / 密度）
    di\                  干声（内容匹配的）
    reamp\               每轮的录音
    notes.md             这首歌的进展记录（测过什么、结论是什么）
```

**工具是通用的，数据是每首歌独立的。**

```powershell
# 统一入口（推荐用 tone.bat，绕开执行策略）
tone.bat list                      # 有哪些歌
tone.bat new "歌名" "原曲.flac"    # 新建一首
$env:SONG_DIR = "songs\<歌名>"     # 切到某首
tone.bat run target_whole.py       # 在它的上下文里跑脚本
tone.bat run analyze_round.py wet.wav
```

**参数形状**：`tone.bat run <脚本> [歌曲目录] [文件/选项]`。
设了 `SONG_DIR` 就只写文件名（`analyze_round.py wet.wav` —— 湿声在 `<歌曲目录>\reamp\` 下）；
没设就写成 `analyze_round.py songs\<歌名> wet.wav`；`--song=<目录>` 是显式逃生口。

### 0.2 工作模式（当前约定，别自作主张改）

**手动加载，不做自动化。**

```
Agent:  生成预设 JSON 文件 → 放到 <包根>\，告诉用户文件名
用户:   复制进预设目录 → 在 GE250 Edit 里加载 → 说"好了"
Agent:  测量 → 分析 → 下一轮
```

**明确不做的事：**
- ❌ 不申请 `<GE250 预设目录>\...` 的写权限（沙箱挡着，也不要绕）
- ❌ 不接 MAAFW / 不做 UI 自动化 / 不模拟点击
- ❌ 不去解决"怎么让软件自动重载预设"
- ✅ 预设文件一律生成到 `<包根>`，由用户手动搬运

**理由**：现在是在验证**算法和闭环**，不是在验证 I/O。加载这一环是临时的桩，将来会被替换——**现在不要为它花任何精力**。

**每轮的握手（不要跳过）：**
1. Agent 说清楚「这次加载哪个文件、预期看到什么」
2. 等用户明确回复"好了 / 加载了"
3. **让用户回读设备屏幕上显示的预设名**——不是问"加载了吗"，是问"屏幕上写的是什么"
4. 才开始测量

**不要假设用户已经加载了。**

**⚠️ 实测事故**：用户说"已加载 3"，设备上其实还是 2 → 同一个预设测了两次
→ **逐频段数据一模一样** → 被误判成"设备参数非线性"，**而且写进了结论**。

> **诊断判据：预期变化与实测变化严重不符时，第一嫌疑是"预设没加载"，不是"设备非线性"。**
> （实测：预期降 3 dB，实测降 0.00 dB）

**预设命名规范**：同一首歌用**递增序号**，不要靠词序区分。
`CSFIX2RV` vs `CSFIXRV2` 只差字母顺序——**这次的乌龙就出在这。**

---

**最重要的一条认知**
> 误差向量里混了三种东西：**源差异 + 内容差异 + 设备可调部分**。
> 只有第三项是**可行动**的。前两项构成"地板"，参数怎么调都消不掉。
> **不要为了让总误差变小而牺牲其他东西**——踩过这个坑，付出了代价（见 §3.9）。
