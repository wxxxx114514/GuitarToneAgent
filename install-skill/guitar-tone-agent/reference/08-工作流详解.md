## 9. 标准工作流

**核心原则：先让目标和 DI 的内容对齐，再谈调参。内容不对齐，后面全是白干。**

```
┌─────────────────────────────────────────────────────────────┐
│ 第 0 步  分析参考曲（每首歌只做一次）                          │
│   分轨 → 吉他轨 → ① 全曲目标曲线  ② 演奏规格                  │
│   演奏规格 = 调性 / 主要和弦 / 奏法比例 / 音区 / 密度           │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ 第 1 步  准备内容匹配的 DI                                     │
│   主：用户按 di_instructions.py 的指令录（定 EQ 的唯一依据）     │
│   辅：合成 DI（gen_palm_di.py）—— 仅供参考，权重低               │
│   verify_di.py 自动检查：电平/调性/调弦/奏法                    │
│   ⚠️ 调性、奏法、和声必须对齐，否则后面测的都是假数字            │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ 第 2-5 步  调参循环（每轮一次 reamp）                          │
│   载入预设 → reamp → 测误差 → 解最小二乘 → 生成新预设           │
└─────────────────────────────────────────────────────────────┘
```

### 9.0 第 0 步：分析参考曲（产出目标 + 规格）

```powershell
# 新建一首歌的工作目录
tone.bat new "歌名" "<音乐目录>\歌.flac"
$env:SONG_DIR = "songs\歌名"

# 分轨（BS-Roformer，GPU ~95 秒/首）→ 输出到 $env:SONG_DIR\stems
$SEP = $env:STEMSEP    # 分离工具路径（包外，需自备）；包内脚本也能代跑：
& $SEP "<音乐目录>\歌.flac" -Out "$env:SONG_DIR\stems"
# 没有 StemSep 时：tone.bat run load_bsr.py "<音乐目录>\歌.flac" "$env:SONG_DIR\stems"

# 目标曲线 + 调性/和弦 + 奏法占比（脚本自己找 SONG_DIR，不用传路径）
tone.bat run target_whole.py
tone.bat run chords.py
tone.bat run technique.py     # ★ 产出奏法占比，决定让用户录什么

```

**产出示例（格式，数值换成当前歌的）**：
```
目标曲线     <歌曲目录>\target.npy            （13 频段，80 Hz–7.2 kHz）
调性         <主音>（<百分比>% 的小节），属音 <音>（<百分比>%）
主要和弦     <和弦列表>
奏法         <闷音 / 开放 的比例>
音区         <把位范围>
密度         <密集段 音/秒>
```

### 9.0.5 第 0.5 步：定起点预设（★ 闭环之前必须先做这一步）

> **§9.2 的循环从「② 载入预设」开始 —— 但那个预设是哪来的？这一步就是回答它。**

**一句话：从【出厂预设】里挑，不要从零搭。**

#### 为什么用出厂预设

**出厂预设就是厂商把几十年经验固化好的「经典配置」（§10.7）。**

实测（同一首歌、同一个目标）：

```
出厂预设 10C J900R     1.77 dB    ← 随便挑的一个，已经很近
出厂预设 12C MARKV RG  2.40 dB
空音色                 3.51 dB    ← 什么都不开
```

**从空音色自己搭，等于把厂商已经做好的工作重做一遍。**

#### 方法：名字定位 + 数据定夺

```
① 定曲风        你直接说，或从参考曲推（失真度 / 频谱 / 奏法）
② 查归档        该曲风下【试过的】预设 → 直接看历史残差
③ 选候选        有历史的挑残差最小的 2~3 个
                没历史的按【名字】挑（名字里就带型号）
④ 各测一次      加载（EQ 归平）→ reamp → 解最小二乘 → 预测残差
⑤ 取最小的      作为闭环的【基准预设】
```

**每个候选只要 1 次加载 + 1 次 reamp** —— 因为有已验证的 EQ 响应模型
（误差 0.43 dB RMS），能软件预测最优 EQ 和残差，不用真迭代两轮。

**判据：不问「哪个听着像」，问「哪个在 EQ 拉满之后残差更低」。**

```
差得少  →  谐波结构对，只是频谱倾斜不对  →  EQ 能修  →  好候选
差得多  →  谐波结构不对，EQ 怎么拉都修不了  →  坏候选
```

#### 为什么名字能当索引

出厂预设的名字里就带型号：

| 名字里出现 | 实际是 |
|---|---|
| `J900R` `JCM800` `PLEXI` `JVM` `JTM45` `AFD` | Marshall 系 |
| `MARKV` `RECT` `JP2C` `TRIAXIS` `LONESTAR` | Mesa 系 |
| `5150` `EVH` | Peavey / EVH 系 |
| `VH4` `FIREBALL` `INVADER` | Diezel / ENGL 系 |
| `SLO100` `UBER` `ECSTASY` `BE100` | Soldano / Bogner / Friedman |
| `TWIN` `DELUXE` `BASSMAN` `PRINCETON` | Fender 系 |
| `AC30` | VOX |

**所以不需要标定「客观特征 → 箱头家族」这种映射** —— 名字本身就是索引。

> **⚠️ 不要扫全部出厂预设。**
> 全部约 200 个 × 1 分钟 = **3 小时**；按名字挑 3~5 个只要 **10~15 分钟**。
> 同家族内部的频谱差异，远小于跨家族的差异 —— 全扫的边际收益很低。
> 同家族内部的细微差别，本来就该由 EQ 闭环去修。

#### ⚠️ 基准预设必须记下来

**后面所有轮次都是相对它改的。** 写进 `notes.md`（§9.5）或 `spec.json`：

```
基准预设: 10C J900R
参数:     AMP Type7(Gain22/Bass40/Mid64/Treble64/Mst55)
          CAB Type5(Mic2/Dist20)  DS-OD Type3(Gain0/Tone50/Vol100)
起点残差: 1.77 dB
```

**换基准 = 前面的轮次全部作废**，必须重头解一遍（见 §9.1 那条「用真 DI 定案时必须回基准预设重新解算」）。

### 9.0.6 归档：每首歌做完就把结果存下来

**目的：让库自然长起来，不用专门花时间扫。**

#### 两个索引维度

```
曲风   →  该曲风下试过哪些预设
预设名 →  每个预设的历史结果
```

#### 存什么

```json
{
  "name": "10C J900R",
  "category": ["J-rock", "rock"],
  "params": { "AMP": {...}, "CAB": {...}, "DS/OD": {...} },
  "sessions": [
    {
      "song": "BlackShout",
      "di": "di.wav",
      "error_13band": [ ... ],      // ★ 方向就在这
      "residual": 1.77,
      "solved_eq": [ ... ],
      "after_eq": 0.55
    }
  ]
}
```

**核心是 `error_13band`（湿声 vs 目标的逐频段误差）** —— 一眼能看出往哪调：

```
1076 Hz +1.34（多了）   3044 Hz −1.32（少了）
   → 方向：中高频不够，1 kHz 偏多
```

#### 三个注意

**① 方向可用于跨歌，绝对值不可**

```
同一个人 / 同一把琴 / 同一种奏法  →  大致能比
换琴 / 换奏法                  →  绝对值不能比
但 "低频肥 / 中频凹" 这种【方向】是稳的  →  仍然可用
```

**② 曲风标签是判断，不是测量** —— 可以多标签，你说是啥就是啥

**③ 每次测完自动写，不用专门做一步** —— 归档是测量流程的副产品

### 9.1 第 1 步：内容匹配的 DI

**两条路。优先让用户录——这是最准的。**

#### 先测参考曲的奏法比例（§7.1 的描述子）

两个量：**低频段（100–450 Hz）占比** + **频谱重心**

```
参考基准（实测）:
  闷音          28.8%  /  1621 Hz
  开放弦        11.4%  /  2000 Hz
  泛音          基频被抑制，低频占比明显偏低
```

逐帧算这两个量 → 聚类 → 得到参考曲里各奏法的**占比**，写进 `spec.json`。

#### 让用户按规格录（唯一路径）

**先确认调弦——这一步必须问用户，不能只靠自动检测**

```powershell
tone.bat run check_tuning.py          # 自动判（仅供参考）
tone.bat run check_tuning.py drop_d   # 用户确认后手动设
```

**为什么必须问**：吉他和弦表在 Drop D / 标准 / 降半音下完全不同。
**实测**：按标准调弦算出的品数**全是错的**——用户弹的是 Drop D，
E5 是"6/5/4 弦全按第 2 品"（一根手指横按），不是"6 弦空弦 + 5 弦 2 品"。

**自动判据只有参考价值**：Drop D 的 6 弦是 D2（73.4 Hz），标准是 E2（82.4 Hz），
比 D2/E2 的出现率。**但吉他轨低音区有贝斯泄漏**（实测 61.7 Hz 的 B1 占 27%，
吉他根本弹不到那个音），所以自动判定会被污染。

**支持的调弦**（`di_instructions.py` 里）：`standard` / `drop_d` / `half_down` / `drop_c`

**强力和弦的按法规则（自动选最低把位）**：
```
Drop D 类：
  根音在 6 弦  →  6/5/4 弦【同一个品】，一根手指横按
  根音在 5 弦  →  5 弦 N 品 + 4 弦 N+2 品 + 3 弦 N+2 品
哪个把位低就用哪个
```

**给用户的指令：用脚本生成，不要手写**

```powershell
tone.bat run di_instructions.py
```

它读 `spec.json`（调性 / 和弦 / 奏法占比），输出**不含任何乐理词汇**的指令：

```
[调弦] Drop D (DADGBE)
==============================================================
   请录一段干声（吉他直接插声卡，中间不要接任何效果器）
==============================================================
总共约 26 秒，分三段。
★ 每段之间【完全停手 1 秒】——手离开琴弦，让声音彻底消失
  （系统靠这个静音自动分段，用来检查你每段弹对了没有）

第 1 段   闷音    约 16 秒
  第一个（弹这个最多）：
      . 第 6、5、4 弦【全部按第 2 品】
      . （一根手指横着压住这三根弦）
  第二个（隔一会儿换过去）：
      . 第 2 粗的弦（第 5 弦）第 2 品
      . 第 3 根弦（第 4 弦）第 4 品
      . 第 4 根弦（第 3 弦）第 4 品
  右手：手掌外侧【轻轻压在琴桥前面】，让声音变成短促的
        "哒哒哒"，不是"当当当"
        中速连续下拨，大约每秒 4 下

第 2 段   还是闷音，换个位置    约 7 秒
      G5：第 6、5、4 弦【全部按第 5 品】
第 3 段   放开手    约 3 秒
==============================================================
```

**段间必须"完全停手 1 秒"** —— `verify_di.py` 靠这个静音自动分段，
才能拿"用户的闷音段"跟"用户自己的开放段"对比（见下）。

**三条设计约束：**

| 约束 | 为什么 |
|---|---|
| **不给乐理词汇**（不写 "E5"、"根音"、"Ⅰ–Ⅴ"） | 用复制音色的多半是小白，写了他也不知道按哪 |
| **给弦号 + 品数**，0 品说"什么都不按" | 这是唯一不会歧义的表达 |
| **三段比例 = 测出来的奏法占比** | 分析结果直接变成"弹多久"，不是另写一套 |

**⚠️ MIDI 基准**：`C2 = 36`，`E2 = 40`。写成 `40 + index("E")` 会得到 G#2，
输出的品数全错（实测踩过）。

**录完之后：先验证，再归一化**

```powershell
$env:SONG_DIR = "<歌曲目录>"
# 录音放进 <歌曲目录>\di\，改名成 palm_di.wav

tone.bat run verify_di.py      # ★ 先验证
tone.bat run meas_prep.py      # 通过后再归一化
```

**`verify_di.py` 检查四件事**（不能退回合成了，那一次录音必须对）：

| 检查 | 判据 | 不对时怎么办 |
|---|---|---|
| **电平** | 不能是静音，不能爆音 | 提醒调声卡输入增益 |
| **时长** | ≥ 15 秒 | 提醒录完三段 |
| **调性** | 主音跟 spec 一致 | 报出实际主音 |
| **调弦** | 反推用户实际用的调弦 | 直接建议改成哪个，并重新出指法 |
| **奏法** | ★ **自参照**：闷音段的低频占比要比开放段高 ≥ 8 个百分点 | 提醒手掌要真正压住 |

**奏法为什么能自参照**：不跟任何绝对基准比，只比"用户自己的闷音段 vs 用户自己的开放段"。
**这样就不需要知道'真实闷音应该长什么样'**，只需要用户前后弹得不一样。

**⚠️ 不要盲减固定 dB**：真实录音的电平跟合成 DI 差很多。
`meas_prep.py` 用 `TARGET_PEAK`（默认 −32 dBFS）**自动归一化**——这个值跟历史所有测量一致。

#### 路径 B（辅助）：合成 DI —— **管线验证夹具，不是音色参考**

> **合成 DI 不是「差一点的 DI」，是「无法验证的 DI」。**
> **它的位置是夹具：证明链路通，不参与音色判定。**

**真正的理由（不依赖任何具体数字）**

```
想验证「这个 DI 弹得对不对」  →  只能跟另一个 DI 比
参考曲那边是【湿声】         →  频谱结构不同（失真堆谐波、混音又高通），比不了
⇒ 除了「用户再录一条」，没有任何办法判断合成 DI 偏了多少

推不出上界的误差  =  不能进优化循环
```

**「仅参考」的根据不是「它错得多」，而是「你无法知道它错了多少」。**
这个理由的好处：**不依赖具体测量值，换个合成算法也不会失效。**

（早先版本写的「低频占比 7.0% vs 97.1%、偏亮 14 倍」**已作废**：
那个对比把干声和湿声混在一起比，类别不同；绝对数值又依赖录音条件，复现不出来，
而且 7.0 / 97.1 这两个数出自已废弃的配方 A / D 两代实现（见 §7.2 的变体谱系）。
**能被后人当标定值引用的数字，必须站得住。**）

**它不可替代的用途：让闭环在用户还没录音时就能跑起来**

| 要验的 | 用合成 DI 能验吗 |
|---|---|
| 发送 PCM 相关性、削顶、对齐、往返延迟 | ✅ |
| 采样率陷阱（44100 / 48000）、`.mo` 格式校验 | ✅ |
| EQ 最小二乘解算、预设生成、握手流程 | ✅ |
| **音色对不对** | ❌ **只有真 DI 能验** |
| **预设之间的相对排序** | ✅ **见下** |

#### ★ 合成 DI 的第二个用途：相对比较（偏差会抵消）

```
输出 = DI 频谱 × 预设传递函数
        D(f)   ×     H_i(f)

比较两个预设：  D·H_i  vs  D·H_j
              比值 = H_i / H_j      ← D 被约掉了
```

**D 是所有预设共有的因子，在比值里自动抵消。**

所以分工是：

| 用途 | 用哪个 DI | 为什么 |
|---|---|---|
| **预设之间排序**（哪个更接近目标） | **合成 DI** | 偏差抵消；快，不麻烦用户 |
| **绝对匹配定案**（最终 EQ） | **真实 DI** | 偏差不抵消，必须用真的 |

> **这也是 §10.7 里「换箱头值不值得」那个实验能用合成 DI 跑的前提。**

**这些用任何 DI 都能验。** 等真 DI 到了，链路已经证明是通的——
**省下的是「在真 DI 上 debug 管线」的时间，那个代价高得多。**

**用它的正确姿势**

```powershell
tone.bat run gen_palm_di.py     # 按 spec.json 的调性生成
tone.bat run meas_prep.py
# ... 确认整条链路能跑通（发送 / 对齐 / 削顶 / 解算 / 生成 / 握手）
# 然后等真 DI 到了，回【基准预设】重新解算
```

#### ★ 用真 DI 定案时：必须回【基准预设】重新解算

**⚠️ 不要从「合成调出来的版本」继续迭代。**

原因：合成版里已经烘焙进了**「补偿合成器缺陷」的那部分 EQ**。
从它继续，那部分补偿会被当成「已经调好的音色」保留下来。

> **必须让最小二乘对真 DI 从零解一次。**

**配套要求**：`notes.md` / `spec.json` 里**逐轮记录「本轮基于哪个 DI」**。
否则三条 DI 混在一起调，回头没人说得清哪个预设是靠什么调出来的。
实测代价：

```
随便弹的开放音阶 + C 和弦     对目标偏差 3.87 dB    ← 60% 是内容差异
按规格弹的闷音（真 DI）       对目标偏差 1.60 dB
```

**内容不对齐时，你测的是内容差异，不是音色差异。而且你会照着这个假误差去调参。**
### 9.2 第 2-5 步：调参循环

```
② 测量        载入预设 → reamp → 得到湿声（先验证无削顶 + 发送 PCM 相关≈1.0）
③ 算误差      湿声的 13 频段包络 − 目标曲线      →  RMS 偏差
④ 解参数      用 EQ 响应模型做【最小二乘】解出各频段需要的单位数
⑤ 生成预设    用文本替换改 .mo（不要重新序列化 JSON，见 §3.3）
   回到 ②
```

**哨兵（每轮都要看）**：
```
削顶        >=0.999 的样本数必须为 0
参数步长    单轮 ≤ ±20 单位（§3.9）
对齐 lag    < 5 ms（异常说明群延迟变了）
MCD         相对基准 ≤ 2×
```

**收敛判定：看【单轮增益塌缩】，不看绝对阈值。**

实测轨迹：
```
总误差      3.53 → 1.60 → 1.51 → 1.49 dB
单轮增益           1.93   0.09   0.02      ← 这个才是信号
```
最终停在 **1.5 dB**，而这首歌的地板是 **2.01 dB**——**已经到地板以下了。**

> **⚠️ 绝对阈值（0.62 dB 量级）会一直给"还差得远"的错误信号。**
> 每个演奏者、每首歌、每套 DI 的地板都不一样。**先量地板，再看单轮增益。**
>
> **判据：单轮增益 < 0.1 dB → 这个维度榨干了，换维度或停。**

### 9.3 每轮的人机握手

```
Agent  生成 xxx.mo 到 <包根>\  并说明：这一轮改了什么、预期从多少到多少
   ↓
用户   复制进预设目录 → 加载 → 回一句"好了"
   ↓
Agent  ★ 请用户【回读屏幕上的预设名】（不是问"加载了吗"）—— 见 §0.2
   ↓
Agent  测量（先验证发送 PCM + 输出峰值！）→ 分析 → 报告 → 下一轮
```

**回报结果时要说清三件事：**
1. 误差变化（实际 vs 预期，以及差值）
2. 有没有触到哨兵（削顶 / MCD / lag / 参数步长）
3. 这一维度还剩多少"可行动"空间

### 9.4 生成预设文件（.mo）的正确姿势

**不要用 `JSON.stringify` 重新序列化**——格式细节太多（§2.2、§3.3）。
**用文本定点替换**：

```javascript
const src = fs.readFileSync("EQFIX2.mo", "utf8");
const a = src.indexOf('"EQ": {');           // 只改这个块
const b = src.indexOf('"Switch"', a);
let block = src.slice(a, b);
for (const [k, v] of Object.entries(NEW_EQ))
  block = block.replace(new RegExp('("' + k + '":\\s*)(\\d+)'), `$1${v}`);
let out = src.slice(0, a) + block + src.slice(b);
out = out.replace('"name": "EQFIX2"', '"name": "FIX5"');   // 名字也换
fs.writeFileSync("FIX5.mo", out, "utf8");   // 不加 BOM，LF，结尾换行
```

**校验清单**（写完必查）：
```
Merge 长度 == 294
fileInfo.name <= 8 字符，纯字母数字
无 BOM / LF 换行 / 以换行结尾
JSON 可解析
跟源文件逐行 diff，应该只有你改的那几行不同
```
