# 手动调音色（任意效果器）

> **⚠️ 这个 skill 是 `guitar-tone-agent` 的附属。**
> 完整方法论（测量协议 / 指标体系 / 内容匹配 / 经典配置 / 标定方法）在 **本 skill 的 `reference/`** ——
> 与 `guitar-tone-agent` 的 `reference/` 是同一份文件（目录联接），改一处两边都生效。
>
> **它只讲两件 GE250 之外才需要的事：**
> **① 怎么从说明书/截图整理出设备规格**
> **② 算完之后怎么让用户手动落地**

> **目标设备没有可编程的预设文件接口，参数只能在设备上手动改。**
> **同一套声学方法论，差别只在「谁来落地参数」。**

```
guitar-tone-agent     预设是文件 → 能直接改 → 全自动迭代
guitar-tone-manual    只能手动拧 → 出表格  → 用户迭代

计算部分（目标曲线 / 误差向量 / 最小二乘 / 哨兵）完全一样
```

## 什么时候用

- 设备不是 MOOER GE250，或者虽然是自己改但拿不到参数文件
- 没有 MIDI 换预设、没有 PC 端编辑器能导出/导入参数
- **参数只能靠人在设备上拧**

## 第一步：拿到设备的「三张表」

**让用户传说明书截图，或设备界面的截图。** 从里面提取：

```
① 模块表   有哪些模块（DS/OD / AMP / CAB / EQ / DELAY / REVERB / …）
② 参数表   每个模块有哪些参数、范围、步进、单位
③ 预设表   有哪些出厂预设、名字、分类
④ 效果链   信号从输入到输出依次过哪些模块
```

> **⚠️ 截图里看不出来的，一律留空并写进 `unknowns`，不要猜。**
> 写错的参数会让用户拧到一个完全错的位置 —— 宁可少写，不可写错。

## 第二步：整理成两个文件（规格 和 状态 分开）

**不要指望能从设备导出 JSON** —— 只能从截图人工整理。但整理结果要结构化。

**分成两个文件，因为两者生命周期不同：**

```
parameter_table.json   设备规格   模块·参数·范围·步进   ← 换更详细的截图就更新
preset.json            当前状态   模块·参数·值         ← 用户改一次参数就更新
```

### `parameter_table.json`（规格，从截图提取）

```json
{
  "device": "<品牌 型号>",
  "source": "manual p.12 截图",
  "confidence": "high | medium | low",
  "updated": "<日期>",

  "chain": ["DS/OD", "AMP", "CAB", "EQ", "DELAY", "REVERB"],

  "modules": {
    "AMP": {
      "types": ["JCM900", "Plexi", "5150"],
      "params": {
        "Gain": { "range": [0, 100], "step": 1, "unit": "", "note": "" },
        "Mst":  { "range": [0, 100], "step": 1, "unit": "", "note": "线性幅度，不是 dB" }
      }
    },
    "EQ": {
      "types": null,
      "params": {
        "100Hz": { "range": [0, 100], "step": 1, "unit": "unit", "note": "dB/单位未标定" }
      }
    }
  },

  "unknowns": ["EQ 的 dB/单位 未标定", "效果链顺序是推断的"]
}
```

### `preset.json`（状态，用户设备上的值）

```json
{
  "device": "<品牌 型号>",
  "preset": "10C J900R",
  "captured": "<日期>",
  "values": {
    "AMP":   { "type": "JCM900", "Gain": 22, "Bass": 40, "Mid": 64, "Mst": 55 },
    "DS/OD": { "type": "TS808", "Gain": 0, "Tone": 50, "Volume": 100 },
    "EQ":    { "100Hz": 42, "250Hz": 67, "630Hz": 38 }
  }
}
```

### 四条规矩

| 规矩 | 为什么 |
|---|---|
| 不确定就留空 + 进 `unknowns` | 写错参数会让用户拧错 |
| `source` / `confidence` 要填 | 判断这表能不能用 |
| **`range` 照抄说明书，不要假设** | 有的设备是 −12~+12 dB，有的是 0-10 档 |
| **规格和状态分两个文件** | 换截图只动规格，改参数只动状态 |

### `range` 的两个用途

```
① 夹紧算出来的值
     最小二乘解出 250Hz 需要 137
     parameter_table 说 range = [0,100]
        → 夹到 100
        → 并告诉用户：这个频段到顶了，修不动，剩下的是源差异

② 检测「到顶了」并如实报告 —— 不要让用户去拧一个拧不到的值
```
## 第三步：把 JSON 转成表格给用户

**JSON 给程序看，用户要看表格。**

```
设备  <品牌> <型号>          来源：说明书截图   置信度：中

效果链  输入 → DS/OD → AMP → CAB → EQ → DELAY → REVERB → 输出

模块      参数        范围      当前值    说明
────────────────────────────────────────────────────
AMP       Gain        0-100       22
          Mst         0-100       55      线性幅度，不是 dB
DS/OD     Gain        0-100        0      推子：Gain 低 / Level 高
EQ        100Hz       0-100       42      dB/单位【未标定】

⚠️ 未确定
   · EQ 的 dB/单位 —— 需要先标定
   · 效果链顺序是从截图推断的，未经确认
```

## 第四步：标定这台设备的 EQ 刻度（一次性）

**GE250 是 0.1848 dB/单位、σ=0.985 八度。别的设备肯定不一样。**

```
固定其他参数，只动一个 EQ 频段：
  unit = min  →  测基准曲线
  unit = max  →  测满刻度曲线
  → 相减得该频段的【增益】和【带宽 σ】
每个频段做一遍 → 得到这台设备的 EQ 响应模型
→ 最小二乘求解那套代码原样能用
```

## 第五步：每轮给一张「拧到几」的表

```
本轮结果：误差 2.1 → 1.4 dB

频段      现在    改成
──────────────────────────
100Hz       42      39
250Hz       67      80
630Hz       38      39
```
**用户照着「改成」那一列拧，拧完回一声，重测。**

## 怎么跟用户说

**要资料时：**

> 你这台不是 GE250，我没法直接改它的参数文件。
> 麻烦给我两类截图：
> ① 说明书里「模块 / 参数」那几页，或者设备界面上的参数界面
> ② 出厂预设列表
> 我整理成表，你确认有没有错。

**交表时（把能做/不能做说清楚）：**

> 表整理好了。两件事说清楚：
> **能做的**：我算得出每个参数该拧到几，跟 GE250 一样准。
> **不能做的**：我没有你设备的文件接口，**改参数得你自己拧**。
>
> 另外你设备的 EQ 刻度我不知道（GE250 是 0.185 dB/单位），
> 需要先标定一次 —— 我出几个测试值，你拧一遍我测一遍就能算出来。

**每轮：**

> 这轮误差从 2.1 降到 1.4 dB。按下面这张表拧：
> （表格）
> 拧完回我一声，我重测。
