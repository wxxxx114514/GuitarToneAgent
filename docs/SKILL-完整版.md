## 0. 先读这一节：这个 Skill 的边界

**做什么**
- 从一首歌里提取吉他音色的**目标指纹**（频谱包络 / 谐波 / 动态 / 空间感）
- 在硬件效果器上通过**修改预设 JSON** → 加载 → 播放 DI → 录制湿声 → 算误差 → 搜参数
- 输出一份能用的预设

**不做什么**
- 不追求「逐样本还原」——**源差异（DI 不同 / 演奏不同）是物理上限**
- 不做软件箱模仿真，一切以**真机测量**为准
- **不做「比人耳更好」的调音**（见 §10.7）

**能力上限（物理的，说清楚免得白费功夫）**

参考录音如果是**真箱 + 麦克风实录**，那么：

```
抓得到：  箱体 + 麦克风的【频响曲线】（这就是 IR 能做的全部）
抓不到：  功放与喇叭的【阻抗交互】（随驱动电平变）
          喇叭大音量下的【非线性】（纸盆形变、压缩）
          麦克风的【近场效应】
          房间
```

**而参考录音是整条链**：`amp → cab → mic → 话放 → 后期 EQ → 压缩 → 混音`。
**中间那几截，模拟抓不到，也调不掉。**

> **所以：撞上这条上限时，正确的做法是承认它，不是继续调。** 判断方法见 §10.7。

### 0.2 工作模式（当前约定，别自作主张改）

**手动加载，不做自动化。**

```
Agent:  生成预设 JSON 文件 → 放到 <包根>\，告诉用户文件名
用户:   复制进预设目录 → 在 GE250 Edit 里加载 → 说"好了"
Agent:  测量 → 分析 → 下一轮
```

**明确不做的事：**
- ❌ 不申请 `<GE250 预设目录>\...` 的写权限（沙箱挡着，也不要绕）
- ❌ 不接 MAAFW / 不做 UI 自动化 / 不模拟点击
- ❌ 不去解决"怎么让软件自动重载预设"
- ✅ 预设文件一律生成到 `<包根>`，由用户手动搬运

**理由**：现在是在验证**算法和闭环**，不是在验证 I/O。加载这一环是临时的桩，将来会被替换——**现在不要为它花任何精力**。

**每轮的握手（不要跳过）：**
1. Agent 说清楚「这次加载哪个文件、预期看到什么」
2. 等用户明确回复"好了 / 加载了"
3. **让用户回读设备屏幕上显示的预设名**——不是问"加载了吗"，是问"屏幕上写的是什么"
4. 才开始测量

**不要假设用户已经加载了。**

**⚠️ 实测事故**：用户说"已加载 3"，设备上其实还是 2 → 同一个预设测了两次
→ **逐频段数据一模一样** → 被误判成"设备参数非线性"，**而且写进了结论**。

> **诊断判据：预期变化与实测变化严重不符时，第一嫌疑是"预设没加载"，不是"设备非线性"。**
> （实测：预期降 3 dB，实测降 0.00 dB）

**预设命名规范**：同一首歌用**递增序号**，不要靠词序区分。
`CSFIX2RV` vs `CSFIXRV2` 只差字母顺序——**这次的乌龙就出在这。**

---

**最重要的一条认知**
> 误差向量里混了三种东西：**源差异 + 内容差异 + 设备可调部分**。
> 只有第三项是**可行动**的。前两项构成"地板"，参数怎么调都消不掉。
> **不要为了让总误差变小而牺牲其他东西**——踩过这个坑，付出了代价（见 §3.9）。

## 1. 硬件与信号链

```
电脑 ──USB──> GE250 ──效果链──> 模拟输出（监听）
     <──USB──  回传（录音）
```

### 1.1 设备端点（Windows / WinMM）

脚本按名字里的 `MOOER` 子串自动查找，**不依赖索引**（索引会变）。

```
输入:  线路 (MOOER STUDIO)          或  线路 (2- MOOER STUDIO)
输出:  扬声器 (MOOER STUDIO)        或  扬声器 (2- MOOER STUDIO)
```

**`2-` 前缀**是 Windows 对"插在不同 USB 口"的命名差异，两种都要能匹配。

### 1.2 GE250 的 USB AUDIO 设置（上位机 SYSTEM 页）

| 项 | 必须的值 | 说明 |
|---|---|---|
| **AUDIO MODE** | **REAMP** | NORMAL 模式下回传收不到效果链输出 |
| LEFT OUT / RIGHT OUT | DRY / DRY（锁死，改不了） | 不影响录音 |
| REC VOL / MIX / PLAY VOL | 50 / 50 / 50 | 先别动，回环通了再看电平 |

**断电会重置这些设置。** 每次设备断电后必须重新确认 AUDIO MODE = REAMP，并**在软件里点一下 NORMAL 再点回 REAMP**（强制重新下发，因为软件显示的状态可能和设备实际状态不同步）。

### 1.3 设备物理属性（实测，跨断电可复现）

| 属性 | 值 | 怎么测的 |
|---|---|---|
| 实时比 | **1.000×** | 10.000 s 音频 → 10.006 s 墙钟 |
| 确定性 | 0.008 dB RMS / 0.022 dB max | 两次相同渲染的频谱差 |
| 固定增益（**空音色**） | **+5.3 dB** | DI 峰值 → 湿声峰值 |
| 固定增益（**高增益音色**） | **约 +32 dB** | 发送 −32 dBFS → 输出 0.00 dBFS（见 §10.6） |
| 往返延迟 | 100–250 ms（会变） | 每次测量都要重新对齐 |
| 压缩比（失真预设） | **约 5:1** | 12 dB 输入 → 2.4 dB 输出 |
| 动态范围 | 失真下几乎不变（12 dB 输入只改频谱 0.3–0.44 dB） | 三档电平测试 |

**实时比 1.000× 是硬约束**：1 次渲染 = 音频时长 + 预设加载（~2 s）。单台设备不能并行。

> **⚠️ 增益随音色变化极大（+5.3 → +32 dB，差 27 dB）。**
> 照 §4.3 的「−30 ~ −35 dBFS」选电平，在空音色下没问题，
> **在高增益音色下必然削顶。** 每次换音色都要重新标定输出峰值（§10.6）。

### 2.2 预设文件格式（⚠️ 极其挑剔）

**真实位置**：
```
<GE250 预设目录>\
```

**沙箱通常不允许写这个目录**（`EPERM`），需要用户手动复制，或申请写权限。

**必须逐字节匹配的格式**（见 §3.2）：

```python
def ser(v, indent):
    pad = " " * indent; pad2 = " " * (indent + 4)
    if v is None: return "null"
    if isinstance(v, bool): return "true" if v else "false"
    if isinstance(v, (int, float)): return str(v)
    if isinstance(v, str): return json.dumps(v, ensure_ascii=False)
    if isinstance(v, list):
        if not v: return "[\n" + pad + "]"
        return "[\n" + ",\n".join(pad2 + ser(x, indent+4) for x in v) + "\n" + pad + "]"
    if isinstance(v, dict):
        if not v: return "{\n" + pad + "}"        # 空对象要展开！
        return "{\n" + ",\n".join(pad2 + json.dumps(k) + ": " + ser(x, indent+4)
                                  for k, x in v.items()) + "\n" + pad + "}"
# 输出时末尾必须加一个 \n
# 无 BOM，LF 换行，4 空格缩进
```

### 2.3 分轨（stem separation）—— 目标曲线的来源

**目标曲线来自分轨后的吉他轨，所以分轨质量是整条链路的前置条件。**

#### 为什么必须分轨

不分离（直接拿全混音当目标）的代价：

```
全混音 vs 吉他轨 的形状差       2.17 dB
我们全部可行动空间              0.62 dB
                              ────────
                              3.5 倍
```

**偏在哪**：全混音在 2–4 kHz 比吉他轨低 2.5–3.9 dB，而**吉他的"拨片咬合感"正好在这个频段**。用全混音做目标 = 主动把 presence 压下去，**正好调反**。

**原因**：混音里吉他只占 **5.3%** 的能量（人声 40% / 鼓 26.5% / 贝斯 25.6%）。

#### 两个模型：时间与质量

**时间（全曲 245.68 s = 4:05）**

| 模型 | 设备 | 全曲用时 | 实时比 |
|---|---|---|---|
| `htdemucs_6s` | CPU | **98 s** | 0.40× |
| **BS-Roformer SW 6-stem** | **GPU (RTX 4060)** | **95 s** | **0.387×** |
| BS-Roformer SW 6-stem | CPU | **约 21–22 分钟** | 5.17× |

**CPU 时间怎么来的**（重要，别搞混）：
- **实测**：30 秒片段 = 155 s（含模型加载），即 **5.17× 实时**
- **推算**：245.68 s × 5.17 ≈ 1270 s ≈ **21.2 分钟**
- **旁证**：全曲跑到 5/38 块时，块速率 34–37 s/块 → 38 × 35.5 ≈ 1350 s ≈ **22.5 分钟**
- **结论：CPU 期望时间 = 21–23 分钟/首（4 分钟的歌）**

**GPU 是 8–13 倍加速，把"绝对不能用"变成"跟 htdemucs 一样快"。**

#### 质量：4 条物理判据（BS-Roformer 赢 3 条）

| 判据 | htdemucs | BS-Roformer | 差 | 谁好 |
|---|---|---|---|---|
| 吉他轨 30–70 Hz（贝斯泄漏） | −49.4 | −53.8 | **−4.4 dB** | BS-Ro |
| 吉他轨 8–16 kHz（镲片泄漏） | −59.8 | −75.5 | **−15.7 dB** | BS-Ro |
| **贝斯轨 2–8 kHz（slap 拨弦区）** | −61.8 | −43.5 | **+18.3 dB** | **BS-Ro** ★ |
| 钢琴轨 30–70 Hz（贝斯泄漏） | −52.6 | −47.6 | +5.0 dB | htdemucs |

**★ 第三条是关键**：**htdemucs 把 slap 的拨弦高频（2–8 kHz）从贝斯轨里削掉了 18 dB**，BS-Roformer 保留了。用户听感"slap 没坏"= 这个 18.3 dB。

**注意**：用**频谱包络**判这两个模型会得出"几乎一样"的错误结论（实测 0.98 vs 0.99 dB）。**必须用物理判据**——见下面的坑。

#### 目标曲线差 0.88 dB

```
46-70s 段，两个模型的吉他轨：
  95 Hz   -2.50 dB   ← 最大（BS-Roformer 低频更少 = 贝斯泄漏更少）
  RMS 0.88 dB   最大 2.50 dB

对比：可行动空间 0.62 dB  → 0.88 dB 是"会影响优化结果"的量级
```

#### 怎么跑 BS-Roformer SW（本地）

**模型不在 audio-separator 的注册表里**，必须用"运行时注册"塞进去：

```python
# load_bsr.py 的核心技巧
_orig = Separator.list_supported_model_files
def patched(self):
    d = _orig(self)
    d.setdefault("MDXC", {})["Roformer Model: BS-Roformer SW 6-stem (local)"] = {
        "filename": "BS-Rofo-SW-Fixed.ckpt",
        "scores": {},
        "stems": ["vocals","bass","drums","guitar","piano","other"],
        "download_files": ["BS-Rofo-SW-Fixed.ckpt", "BS-Rofo-SW-Fixed.yaml"],
    }
    return d
Separator.list_supported_model_files = patched
```

**为什么能行**：`download_file_if_not_exists()` 第 560 行——**文件已存在就跳过下载**。所以只要 ckpt/yaml 已经躺在 model_file_dir 里，注册表里补个条目就能加载。

**跑法**：
```powershell
$env:PATH='<包根>\_env\ffmpeg;' + $env:PATH
& '<包根>\_env\venv_gpu\Scripts\python.exe' `
  '<包根>\tools\load_bsr.py' <输入音频> <输出目录>
```

**模型来源**（GitHub 上 404，实际在 HuggingFace）：

#### 依赖坑（GPU venv 搭建）

`uv pip install audio-separator` **不会自动装全依赖**。缺了要在报错时逐个补：

```
onnxruntime      ← 不装直接 ModuleNotFoundError
audioread        ← uvr_lib_v5/spec_utils.py 需要
beartype einops julius ml_collections pydub resampy samplerate scipy six tqdm requests
```

**`diffq` 需要编译，会撞 uv 缓存的权限错误 → 不要装**（它只用于模型压缩，推理不需要）。

#### ⚠️ 分离质量的判据：**不要用频谱包络**

**踩过的坑**：我最初用"吉他轨的频谱包络"评判两个模型，得出"几乎一样（0.98 vs 0.99 dB）"，据此否决了 BS-Roformer。

**错在哪**：频谱包络测的是"整体频率分布"，**测不出"内容纯度"**（吉他轨里混进了多少别的东西）。而用户一耳朵就听出 slap 变好了。

**正确的判据（都是物理判据，不会骗人）**：

| 判据 | 方法 | 原理 |
|---|---|---|
| **贝斯泄漏** | 吉他轨 30–70 Hz 与贝斯轨的相关 + 电平差 | **吉他最低音 E2 = 82.4 Hz，30–70 Hz 不可能是吉他** |
| **镲片泄漏** | 吉他轨 8–16 kHz 的电平 | 吉他泛音到不了那么高 |
| **乐器缺失** | 该乐器的主频段能量够不够 | 反向检查"该给的有没有给" |
| **合成器泄漏** | 吉他不响的帧里，吉他轨的残余 | 那时候的能量只可能是漏的 |

**且测相关性时要注意**：贝斯和吉他跟鼓是同步的，**节奏本身会造成互相关**。要在"吉他没在弹"的帧里测，才能排除节奏混淆。


---


#### ★ 分轨质量自检（加总还原度）—— 每首歌做一次，很快

**判据**：六轨相加，跟原曲逐频段比相关；再查轨间相关。

```
六轨相加 vs 原曲    60Hz–12kHz 各频段相关  应 0.99+
轨间相关            吉他 vs 贝斯 / 鼓 等    应 ≈ 0
```

**为什么这条比 §2.3 上面的泄漏判据更好用**：
- 泄漏判据要知道「吉他弹不到哪个音」才能判（有乐理门槛）
- 加总还原度只看数字，**0.99 就是干净，0.8 就是模型在瞎分**

**实测（BS-Roformer SW 6-stem）**：0.99+，轨间 ≈ 0 ✓

## 3. ⚠️ 陷阱清单（每条都真实踩过，代价以小时计）

### 3.1 PowerShell 的 `-shl` 在 `[byte]` 上会截断

```powershell
[byte]0xFF -shl 8       # = 0        type=Byte   ← 静默归零！
[int][byte]0xFF -shl 8  # = 65280    type=Int32  ← 正确
```

**后果**：24-bit PCM 转换时只剩最低字节，发出去的信号比原信号低 **74 dB**，跟原信号相关系数 0.03。
**症状**：设备收到的是垃圾，用户听到"噪声"而不是拨弦声。
**修法**：所有位移前先 `[int]` 强转。**更好的修法：把转换挪到 Python（§3.2）。**

### 3.2 PowerShell 逐样本循环太慢

57.6 万次迭代（12 秒音频），每次做字节运算 + `Array::Copy`，PowerShell 解释器扛不住 → 命令超时被杀。

**修法**：**Python 做转换写 WAV，PowerShell 只负责播放**（`meas_prep.py` + `reamp2.ps1` 的分工）。

### 3.3 预设 JSON 的 `Merge` 数组**必须正好 294 项**

- 写成 300 → **软件整个文件读不进去**（不报错，就是列表里看不到）
- 空对象 `{}` 要展开成 `{\n    }`
- 文件末尾**必须有换行符**

**验证方法**：拿一个软件自己导出的文件，解析后重新序列化，**必须逐字节相同**。做到这一点再生成新文件。

### 3.4 预设名 `fileInfo.name` ≤ 8 字符，别用下划线

- `EQCAL_100`（9 字符）→ 读不出
- `US CLEAN`（8 字符）、`EQFIX2`（6 字符）→ 正常
- **下划线疑似也有问题**，用纯字母数字最稳（`CAL1`、`FIX4`）

### 3.5 每次测量前必须验证"发出去的 PCM"

**这是最重要的一条纪律。**

```bash
# 转完之后立刻验，跟原 DI 比
原始 DI   峰值 -15.76 dBFS
发出的    峰值 -15.76 dBFS     ← 必须一致
最大逐样本差 0.0000
相关系数     1.000000          ← 必须 ≈ 1.0
```

**相关系数 < 0.99 就停手，别往下走。** 否则你会在垃圾数据上分析一整天。

### 3.6 判断"回环是否通"要用**相关系数**，不是电平

| 现象 | 含义 |
|---|---|
| 相关系数 ≥ 0.3 | 真的回录 |
| 相关系数 < 0.1 | 没回录，录到的只是底噪 |
| 电平 −80 dBFS 但相关系数 0.9 | 信号很弱但真实 |

**强失真信号的相关性天然会降到 0.3 左右——不要因为相关性低就判"回环断开"，先看电平。**

### 3.7 设备断电会重置 reamp 设置；软件显示的状态可能不同步

重新上电后：**在软件里点一下 NORMAL，再点回 REAMP**，强制重新下发。

### 3.8 设备索引会变

输出设备索引在 #0 / #3 / #4 之间跳（因为 Windows 重新枚举）。**永远按名字匹配，不按索引。**

### 3.9 **不要为了压指标而大跳参数**（血的教训）

```
J900R原版 → EQFIX1   参数变化 +13/+29/+12/+19/+16   用户：没提问题
EQFIX1   → EQFIX2   参数变化  −3/ +6/ −6/ −1/ +3   用户：和原版差不多
原版      → FIX3     参数变化  −3/+53/ −8/+31/ +9   用户：有电音 ★
```

**大跳参数会产生听得出、但指标测不出的伪影。**
**约束：每轮每频段变化 ≤ ±20 单位，多轮小步迭代。**

**⚠️ "±20 单位 = ±3.7 dB" 只对 EQ 成立。**
AMP / Volume 类是**线性幅度**：`Mst` 55→35 是 −3.9 dB，
35→15 是 −7.4 dB。**同样 20 单位，低值区能到 7 dB。**（见 §10.5）

### 3.10 JS 模板字符串会吃掉反斜杠

写 PowerShell 路径时用 `String.raw`，否则 `'<包根>\_env\winmm.cs'` 会变成 `'D:project_stemswinmm.cs'`。
同理，**PowerShell 里的反引号别写在 JS 模板字符串里**。

### 3.11 `.ps1` 执行策略

不能直接 `-File` 运行。用：
```powershell
& ([scriptblock]::Create((Get-Content 'xxx.ps1' -Raw -Encoding UTF8)))
```
脚本内容**尽量用 ASCII**，中文在 ANSI 解析下会乱码。

### 3.12 ⚠️ 采样率：stems 是 **44100**，reamp 录音是 **48000**

**这个坑我踩了两次。**

```
BS-Roformer / htdemucs 输出   →  44100 Hz   （跟原曲一致）
reamp 录音（设备回传）        →  48000 Hz   （设备固定）
```

**写错会同时歪掉时间轴和频率轴（8.8%）：**
```
把 44100 的信号按 48000 解释：
  时间标签偏 8.8%     写"10-28s"实际是 10.9-30.5s
  频率标签偏 8.8%     写"30-70Hz"实际是 27.6-64.3Hz
```

**纪律**：读任何音频后立刻 `assert sr == SR`，别信全局常量。

```python
x, sr = sf.read(p, always_2d=True, dtype="float32")
assert sr == SR, "%s 采样率 %d != %d" % (p, sr, SR)
```

### 3.13 ⚠️ `sf.read` 不加 `always_2d=True` 会在立体声上炸

`meas_prep.py` 原来没加，遇到立体声 DI 时 `np.stack` 会产出 3 维数组。
**之前的 DI 都是单声道，所以一直没暴露。** 用 `meas_prep.py`（已修）：

```python
x, sr = sf.read(DI, always_2d=True, dtype="float32")
mono = x.mean(1)            # 立体声 -> 单声道
```

### 3.14 ⚠️ PowerShell 脚本的五条铁律（写工具时必看）

做 `<StemSep 目录>` 独立工具时踩出来的，**代价 8 轮调试**。详见 `<StemSep 目录>\README.md`：

```
① 脚本含中文必须配 UTF-8 BOM（且加 BOM 前先剥掉已有的，否则双 BOM
   的症状跟没加 BOM 一模一样）
② 参数名避开自动变量（$Input / $Args / $Error / $Host / $PWD）
③ 包装原生命令别用 $ErrorActionPreference = 'Stop'

### 3.15 ⚠️ 分轨会把混响尾巴掐成精确 −240 dB 全零

歌曲结尾实测：

| 轨 | 262 s 时电平 |
|---|---|
| 母带 | −68 dB（还有尾巴） |
| guitar / bass / vocals | **−240 dB（精确全零）** |
| drums | −74 dB |

**含义**：
- **分轨里没有混响信息，混响只存在于母带。** 测参考曲的空间感必须用母带。
- 顺带：**分轨的"静音段"不等于原曲静音段**，别拿它当噪声门限。

### 3.16 ⚠️ 参考曲的混响真值可能根本测不到

实测一首 266 秒的歌：只有 3 个干净收尾点（密度 1.38 音/秒），
三点 RT60 差 **6 倍**（0.24 / 1.47 / 0.67），其中两个尾音中位 **−98 dB**（数字静音）；
母带唯一的干净衰减是整体淡出（259–263 s 稳定 −9 dB/s，264 s 硬切静音），
读出 2.5–6.7 s，**物理不可信**；唯一可信的候选点（215.2 s）**吉他还在弹**。

**第二个会话（266 秒的歌）的完整证据链**：

```
干净收尾点：全曲只有 3 个
三个点 RT60：0.24 / 1.47 / 0.67 s   —— 差 6 倍，不可信
其中两个尾音中位：−98 dB（数字静音，测的是噪声）
母带唯一干净衰减：259–263 s 整体淡出（稳定 −9 dB/s），264 s 硬切静音
   -> 读出 2.5–6.7 s，物理不可信（那是淡出曲线，不是房间）
唯一可信候选点：215.2 s   —— 但吉他还在弹
```

**结论**：周边层没有可优化对照的真值时：
**只标定器件端 + 选一个合理的值，写清楚"这一层是选的，不是测出来的"。**

> **不要为了凑一个 RT60 数字去用淡出段** —— 那会把「工程师的推子」
> 当成「房间的混响」写进结论。**没有真值就说没有。**

### 3.17 ⚠️⚠️ 不要用"读出来再写回去"的方式改文件

> **读工具对长文件有【静默截断】——实测上限 30530 字符。**
> 超出部分不报错、不提示，你会以为读全了。
>
> 本次后果：备份是截断的 → 回写把 §10.3 后半 + §11 + §12 + §13 **全删了**。

**正确做法**：

改文件    定点替换（锚点唯一才动手），不要整文件重写
改完立刻  核对：总行数 / 二级标题数 / 代码围栏是否偶数配平
```

**验证截断确实存在的方法**（本文件实测）：
```

read  1222 行 / 30530 字符   ← 少了 150 行，静默
```

### 3.18 ⚠️ PowerShell 5.1 的 `Get-Content` 按 CRLF 切行——LF 文件会被当成【一行】

**症状**：配置文件用 LF 换行写入，`Get-Content` 读出来整个文件是一行，
注释和值粘连在一起，然后被 `StartsWith('#')` 之类的过滤条件整条丢掉。
**安静失败**——不报错，只是配置不生效。

实测（`python_path.txt`，4 行 LF）：
```
[1] '# 告诉 tone.ps1 用哪个 Python。 # 优先级：...'      <- 两行粘一起
[2] '# 改这一行即可。<包根>\_env\venv\...'    <- 注释和路径粘一起
                                                       -> 被过滤掉，路径丢失
```

**修法（两条都做）**：

```powershell
# 1) 数据文件用 CRLF 写
'line1','line2' -join "`r`n" | Set-Content -LiteralPath x.txt -Encoding UTF8

# 2) 读的时候自己切，两种换行都兼容
$txt = Get-Content -LiteralPath x.txt -Raw -Encoding UTF8
($txt -split "`r?`n") | ForEach-Object { ... }
```

> **凡是给 PowerShell 读的数据文件（配置、清单、路径表），一律 CRLF。**
> `.ps1` 脚本本身 LF 也能跑（有 BOM 即可），但**数据文件不行**。

## 4. 测量协议

### 4.1 分层测量（必须）

| 层 | 测什么 | 预设要求 |
|---|---|---|
| **核心音色** | 频谱包络、谐波结构、动态压缩、增益 | **关掉 REVERB / DELAY** |
| **周边** | RT60、延迟时间、混音比 | 单独测，用**孤立脉冲** |

**为什么必须分层**：混响对**谐波测量**的污染可达 3.65–8 dB。

**对「时均频谱包络」的污染：0.5–1.1 dB**（两个会话、两首歌、不同混响设置各测一次：
0.47 dB / 0.90–1.02 dB）—— **比谐波层小一个量级，测包络时可以忽略。**

> **量级结论稳定，绝对数值随混响设置变。** 换歌/换 reverb 参数时按 1 dB 量级估，
> **不要当标定值引用。**

> **⚠️ "周边"这一层可能根本测不到参考端的真值** —— 见 §3.16。
> 分轨会把混响尾巴掐成精确全零（§3.15），母带上的干净衰减又常常不存在。
> **没有真值时：只标定器件端 + 选一个合理的值，并写清楚"这一层是选的，不是测出来的"。**

### 4.2 测混响要用孤立脉冲

音乐信号测不出 RT60（音符本身的衰减和混响混在一起）。
**发一个短脉冲 + 长静音**，直接从冲激响应里读：
```
0.5s 静音 → 10ms 带限脉冲(1-8k) → 5s 静音
```

**★ 重复性判据：连测 4 次，极差应 < 0.02 s。**

实测（REVERB Decay=30）：**0.47 / 0.47 / 0.46 / 0.47 s**，极差 0.01 s —— 这个量级才算测住了。
**极差大于 0.05 s 说明没测准**（脉冲被截、混响没跑完、或环境噪声），重测。

**衰减不是单一指数**：实测 0.05–0.15 s 段 154 dB/s，0.30–0.50 s 段降到 80 dB/s
（扩散尾）。**报 RT60 要说明取的是哪一段。**

**⚠️ 脉冲电平必须跟发送信号共用同一个归一化目标（−32 dBFS）。**
整条链实测增益 **+32 dB**（见 §1.3 / §10.6），
**−6 dBFS 的脉冲必然削顶**——那样测的是削顶后的冲激响应，不是器件的。

### 4.3 电平选择

送出去的电平决定放大器的工作点（实测 5:1 压缩）。
- 高增益预设：**−30 ~ −35 dBFS 峰值**（避免输出削波）
- 先跑一次空音色标定固定增益，再按需要衰减

**为了保护耳朵**：默认 `DI_GAIN = -14 dB`；正式测量前先发 1 秒低电平探针让用户确认音量。

### 4.4 对齐

每次测量都要重新对齐（往返延迟会变，实测 **100–250 ms**）。
互相关搜索范围取 **±300 ms**——必须覆盖往返延迟的上界。

**⚠️ 窗口开小了会误判"回环断开"**（实测事故）：
搜索范围 ±60 ms 时，最佳 lag 落在 **+49.44 ms**（正好是窗口边界），
相关系数掉到 **0.002**，差点判定设备坏了。
**设备正常时相关系数应在 0.6 左右**（实测 0.619 / 0.654）。

> **诊断判据：lag 出现在搜索窗口的边界上 = 窗口开小了，不是设备有问题。**

**对齐 lag 本身就是诊断量**——见 §6.4。

### 4.5 噪声审计（每首歌开工时做一次）

**链路每一环都量一次静音段**（`noise_audit.py`）：

```
① 用户录的 DI        信噪比应 > 40 dB
② 湿声录音          应 > 80 dB（设备有噪声门，实测 82–86 dB）
③ 分离后的吉他轨     比较两个模型在"吉他静音段"的残余
                     —— 差值就是泄漏量（实测 BS-Roformer 比 htdemucs 干净 63 dB）
④ 合成 DI（如果用了） 应该是完美数字静音（−240 dBFS），不是的话生成器有问题
```

**⚠️ 工频必须在【静音段】里量。**
在音乐段落里量会撞上音符——**实测：120 Hz 的测量撞上了 B2（123.5 Hz），得出假结论。**

**实测基线**（可作参考）：
```
用户录的 DI（开放演奏）   SNR 64.8 dB   工频 50Hz 相对信号 −52 dB
湿声录音                  SNR 83.5 dB   （设备噪声门）
BS-Roformer 吉他轨        −240 dBFS（数字静音）
htdemucs 吉他轨            −42.5 dBFS  ← 吉他静音段仍有残余 = 泄漏
```

## 5. 两层指标架构（核心设计）

**参考音频和渲染输出的【内容不同】，所以不能直接逐帧比较。必须分两层：**

```
┌─ 外层（对参考）─────────────────────────────┐
│ 参考 vs 渲染：内容不同、奏法可能不同          │
│ 指标：时均包络（1/3 或 1/6 倍频程）           │
│       × JND权重 × 可行动性 × 地板惩罚         │
│ 作用：定方向、判"这个维度榨干了没有"          │
│ 盲区：混响（时均把它平均掉了）                │
└──────────────────────────────────────────────┘
┌─ 内层（候选之间）───────────────────────────┐
│ 同一个干声过不同预设：内容完全相同 ✓          │
│ 指标：LSD / LogMelMSE / MCD / SC / MultiRes  │
│ 对齐 lag（= 群延迟）当伪影哨兵                │
│ 作用：雅可比 J、伪影检测、精调                │
│ 优势：混响【可见】，对跑偏极敏感              │
└──────────────────────────────────────────────┘
```

### 5.1 逐帧指标的实测灵敏度

以 J900R原版为基准（同一干声）：

| 候选 | LSD | LogMelMSE | MCD | SC | MultiRes |
|---|---|---|---|---|---|
| EQFIX1 | 10.66 | 1.10 | 208.8 | 0.163 | 5.04 |
| EQFIX2 | 12.87 | 1.97 | 213.7 | 0.166 | 5.29 |
| **FIX3** | **20.37** | **8.38** | **562.1** | **0.308** | **8.04** |
| 倍数 | 1.58× | **4.24×** | 2.63× | 1.85× | 1.52× |

**5/5 个指标都把有问题的 FIX3 判出来了**（而时均包络只差 0.29 dB）。

### 5.2 混响在逐帧指标里是可见的

同一个干声，一个过混响预设一个没过：

| 指标 | 时均包络 | LSD | MCD |
|---|---|---|---|
| 数值 | **0.47 dB** | 6.04 | 79.6 |

**时均看不见，逐帧看得见。** 所以：**内层用逐帧，混响自动纳入优化；外层要用混响，得靠独立的 `reverb: {rt60, tail_ratio}` 块。**

## 6. 误差向量与加权

### 6.1 结构

```
e(f) = 目标包络(f) − 实测包络(f)          （外层用）
e_frame = 逐帧指标向量                     （内层用）
```

### 6.2 分解：地板 vs 可行动

**方法：在参数空间采 N 个点，看误差向量的统计量。**

```python
地板     = mean(e_i)     # 不随参数变化 → 源差异 + 内容差异，修不掉
可行动   = std(e_i)      # 随参数变化   → 真正的优化空间
```

**实测（4 个预设）：**
```
地板 RMS   1.36 dB
可行动 RMS  0.62 dB
```

**各版本位置：**
| 版本 | 总误差 | 地板分量 | 可修正分量 |
|---|---|---|---|
| J900R原版 | 1.77 | 1.56 | 0.85 |
| EQFIX1 | 1.40 | 1.37 | 0.28 |
| **EQFIX2** | 1.23 | 1.20 | **0.26** ← 贴到地板了 |
| FIX3 | 1.52 | 1.31 | 0.77 ← 跑开了 |

**停止判据：单轮增益 < 0.1 dB（见 §9.2），不是总误差 < 阈值。**

**⚠️ 采样点必须【分散】，不能沿同一个方向采。**
只在一条线上采（比如只调 EQ），算出的"可行动"会被**系统性高估**——
因为它测的只是那一个方向的变化量。
**几个维度各动一动**（EQ / 增益 / 压缩），采样矩阵才代表参数空间。

### 6.3 频段加权

```python
w(f) = JND权重(f) × 可行动性(f) × 地板惩罚(f)
# JND权重: 1/jnd(f)，500Hz-5kHz 最敏感
# 可行动性: std(e)/(mean(std))  —— 参数能改变的幅度
# 地板惩罚: 1/(1 + (|mean(e)|/std(e))²)  —— 地板大说明修不了
```

**实测权重（存于 `band_weights.npy`）：**
```
 761 Hz   地板 +2.46  可行动 0.20  →  权重 0.006   （修不了，忽略）
4305 Hz   地板 −0.11  可行动 1.06  →  权重 4.72    （能修，重点盯）
```

### 6.4 伪影哨兵

| 哨兵 | 判据 | 实测 |
|---|---|---|
| **对齐 lag（群延迟）** | 正常 < 1 ms；异常 > 5 ms | FIX3 = **6.19 ms**，其他 < 1 ms |
| **MCD** | 相对基准 > 2× | FIX3 = 2.63× |
| **参数步长** | 单轮 ≤ ±20 单位（注意 §3.9 的适用范围） | FIX3 跳了 +53 |
| **输出峰值** | 必须 < **−0.1 dBFS** | 贴着 0.00 本身就是警报——削顶数为 0 只是运气（§10.6） |

## 7. 奏法处理

### 7.1 只有两种奏法真正改变频谱

| 奏法 | 改频谱吗 |
|---|---|
| **闷音** | ✅ 大改（低频厚度 +、高频砍、衰减短） |
| **泛音**（自然/人工） | ✅ 大改（基频被抑制） |
| **力度** | ❌ 不改频谱（实测 12 dB 输入只改 0.3–0.44 dB） |
| 推弦/滑音/揉弦/点弦/扫弦 | ❌ 不改（纯音高域或瞬态） |

### 7.2 奏法不匹配 = 比对结果无效

**实测证据：**
```
全曲比对（奏法混杂）  1.23 dB  →  用户听不出差别（特征被平均掉了）
闷音比对（奏法对齐）  1.41 dB  →  暴露出 2-3 kHz 有 5 dB 的真实差距
```

**所以必须：**

1. 描述子检测：**低频占比（100–450Hz）+ 频谱质心** 能把闷音和开放弦分开

   **★ 配方钉死在 `songlib.technique_descriptor()`，所有脚本调同一个实现。**
   文档里的数字会因为重新实现而漂移，代码不会。

   ```python
   DESC_RECIPE = {
       # ---- 聚合顺序 ★★★ 最大的一格（实测同输入差 11 点）----
       "aggregation": "per_frame_then_stat",
       #   "per_frame_then_stat"  逐帧算比值/质心，再跨帧统计
       #   "pool_then_ratio"      先池化频谱，再从池化谱算比值/质心

       # ---- 域（两种聚合下语义不同，故拆两格）----
       "per_frame_domain": "power",     # per_frame 下："power" | "amplitude"
       "pooled_domain": "power",        # pool 下：
       #   "power"          池化 |X|^2 再算比值           -> 86.0%
       #   "amplitude"      池化 |X|   再算比值           -> 66.3%
       #   "rms_amplitude"  池化 |X|^2 后【逐 bin 开方】  -> 61.6%   ★ 别混

       # ---- 跨帧统计（仅 per_frame 有效）----
       "frame_statistic": "median",     # "median" | "mean"

       # ---- 时频 ----
       "n_fft": 8192,  "hop": 4096,  "window": "hann",  "gate_db": -60.0,

       # ---- 频段与分母 ----
       "band_lo": 100.0,  "band_hi": 450.0,
       "denominator_hi_hz": None,      # None = 到 Nyquist
       #   ⚠️ 「分母上限无影响」只对【干声】成立（6k 以上没能量）。
       #      失真湿声在 10k 以上有大量谐波 —— 用湿声测时必须重新确认。

       "recipe_version": "2026-09-28/b",
   }

   低频占比 = 100 × sum(V[100:450]) / sum(V[全谱])   V 由 aggregation/domain 决定
   频谱质心 = sum(f·V) / sum(V)                      同上
   ```

   **整组变体的谱系**（同一份 di.wav，由 recipe_version=2026-09-28/b 复现）：
   ```
   A pool + rms幅度        61.6% / 652 Hz
   C pool + 平均幅度       66.3% / 582 Hz
   G 逐帧 + 幅度 + mean    73.3% / 511 Hz
   F 逐帧 + 幅度 + median  75.8% / 467 Hz
   B pool + 平均功率       86.0% / 307 Hz
   E 逐帧 + 功率 + mean    90.9% / 298 Hz
   D 逐帧 + 功率 + median  97.1% / 325 Hz   ← 本配方
                          跨度 35.5 点
   ```

   **各格权重（di.wav，只改一处）：**

   ```
   聚合顺序（per_frame vs pool）   功率域内差 11 点      ← 最大 ★
   域（功率 / 幅度 / RMS幅度）     ~20~25 点，质心 2 倍
   统计量（median / mean）         6~8 点
   门限（有 / 无）                 3~4 点
   窗长 2048~16384                 ~1 点
   hop                             0
   分母上限 6k~24k                 0（★ 仅对干声成立）
   ```

   > **一个阈值取决于实现的守卫，不是守卫。**
   >
   > **引用规矩：本文档里的描述子数值，只有带 `recipe_version` 的才可引用；**
   > **其余裸百分数（含早先所有版本）一律「来历不明，勿引用」。**
   > 所以：**配方写进代码，不写进文档；文档只负责指向代码。**

   **锚点（必须挂在实现版本上，不能是裸的百分数）：**

   ```
   由 songlib.technique_descriptor() 于 recipe_version=2026-09-28/b 测得
   （样本：某首歌的吉他轨，湿声）

     类别    帧数     低频占比      质心
     闷音    1315     37.5%      1388 Hz
     中间     599     18.1%      1785 Hz
     开放     254     10.9%      2000 Hz

   分类阈值: 低频>22% 且 质心<1800 -> 闷音
             低频<15% 且 质心>1800 -> 开放
   ```

   > **⚠️ 阈值也是锚点的一部分。** 换实现（改聚合顺序、改域、改统计量）
   > 这些数会一起漂 —— **必须整组重新标定，不能只改一半。**
   >
   > 旧文档里的裸数字（闷音 28.8% / 1621 Hz）**已作废**：说不清是哪个实现量的。

   > **⚠️⚠️ 绝对锚点【只用于湿声】；干声一律【自参照】。**
   >
   > 干湿不可横向比（失真堆谐波、混音又高通）。
   > 本节锚点全是在【吉他轨（湿声）】上量的；干声是另一个量级：
   > ```
   > 由 recipe_version=2026-09-28/b 测得：
   >   用户真实录音（干声）   88.6–97.1% / 262–325 Hz
   >   合成 DI（干声）         6.4% / 2924 Hz
   > ```
   > **这些数不能当干声的绝对闸门。**
   >
   > `verify_di.py` 的奏法检查正是**自参照**设计
   > （用户的闷音段 vs 用户自己的开放段，只比差值不看绝对值）——
   > **那是唯一在干声上成立的判据。后人不要改成绝对阈值。**

2. **不确定就问用户**——「这段是闷音还是开放？」（一句话 5 秒，猜错一轮 5 分钟）

3. **可比性守卫**：描述子不匹配时**拒绝出结果**，不要给一个偏大的误差
   （那会被误当成「音色还没调好」）

### 7.3 【内容匹配】—— 今天最重要的方法论 ⭐

**比对要成立，DI 的内容必须跟目标的内容同分布。三个维度：**

| 维度 | 不匹配的后果 | 怎么匹配 |
|---|---|---|
| **奏法** | 闷音 vs 开放，低频段占比差 2.5 倍 | §7.1 的描述子测出参考曲的奏法比例 |
| **调性** | 基频不同 → 13 个频段错位 | 从参考曲测调性（chroma），DI 用同一个调 |
| **和声** | 弹的和弦不是参考曲的和弦 | 和弦模板匹配，找出主要和弦 |

#### 实测代价（同一个预设 EQFIX2，同一个全曲目标）

```
DI 内容                              对目标的偏差
开放音阶 + C 和弦（不匹配）           3.87 dB
E/B 强力和弦闷音（匹配）              1.60 dB
                                     ────────
                                     2.27 dB 全是内容差异
```

**换句话说：内容不匹配时，测出来的"音色误差"里有 60% 是假的。**

#### 调性差多少算差

```
F# 调 DI  vs  E 调 DI（同样的奏法、同样的和声结构）
→ 包络差 RMS 0.78 dB，95 Hz 处最大 2.36 dB

对比：可行动空间 0.62 dB
```

**所以调性必须匹配。** 隔一个半音就会引入跟可行动空间同量级的偏置。

### 7.4 目标曲线：用全曲，不要只用闷音段

**早先的做法**是"只挑跟参考窗口形状接近的段落"（形状距离 < 2.0 dB）。**这会导致过拟合**——目标只代表闷音，调出来的预设也只对闷音好。

**实测：全曲吉他轨的段间一致性**

```
每 20 秒一段，与全曲平均的偏差：
   0-20s   5.30 dB   ← 前奏独奏，唯一的例外
  20-220s  0.43 ~ 1.47 dB
  中位 0.87 dB   p90 1.45 dB
```

**结论：除了前奏，全曲音色一致，可以直接用全曲当目标。**

**全曲目标 vs 闷音窗目标：RMS 0.60 dB，最大 1.14 dB**（主要在 190–537 Hz，全曲目标要**更多**低中频）。

**过拟合的教科书案例（FIX4）**：

```
              闷音 DI（训练场景）    开放音阶/C 和弦（场景外）
EQFIX2            1.41 dB              3.32 / 2.55 dB
FIX4              0.84 dB              3.87 / 3.35 dB
                 ─────────            ──────────────
                 改善 0.57 dB          变差 0.55 / 0.80 dB
```

**训练集赚 0.57，场景外亏 0.55–0.80。净负。**

### 7.5 标准 DI：怎么造一个内容匹配的干声

**优先顺序：**

1. **【主】用户按指令录** —— 定 EQ 的唯一依据（见 §9.1）
2. **【辅】合成 DI** —— **管线验证夹具，不参与音色判定**（见 §9.1）。
   理由不是「它错得多」，而是**「你无法知道它错了多少」**：
   参考曲是湿声，结构不同比不了，除了让用户再录一条没有别的验证方式。
   **推不出上界的误差不能进优化循环。**
3. ❌ **不要用随手弹的东西**——内容不匹配，测出来的数字有 60% 是假的

## 8. 已证伪的路线（别再试）

### ❌ 8.1 去混响（dereverb）

**四个独立模型，四种架构，全部让频谱更差：**

| 模型 | 频谱偏移 | vs 未处理 | 备注 |
|---|---|---|---|
| 未处理（只有混响） | **0.45 dB** | — | 病很轻 |
| Reverb_HQ_By_FoxJoy | 1.55 | +1.10 | |
| UVR-DeEcho-DeReverb | 1.55 | +1.10 | |
| UVR-De-Echo-Aggressive | 1.59 | +1.14 | 硬门限（动态范围 177 dB） |
| UVR-De-Reverb-aufr33 | 1.61 | +1.16 | 同上 |

**真机混响重测（排除"合成混响不真实"的质疑）：**
```
真值：干声  |  输入：干声 + 真机混响  |  未处理偏移 0.47 dB
dereverb 输出 vs 干声：1.24 / 1.25 dB   → 还是更差
```

**操作性判据（最直接）：**
```
我们的输出  vs 带混响参考    vs 去混响参考
  0.85              1.54        ← 去掉混响反而差 81%
```

**原因**：混响对频谱包络的影响只有 0.47 dB，而 dereverb 会砍掉 **95 Hz 附近 4 dB**——那是闷音的低频冲击，**是音色本身不是混响**。

### ❌ 8.2 用包络自相关测延迟

```
我的链路【完全没有 delay】，自相关却在 250/500/750/1000 ms 出峰
→ 那是干声的 250ms 扫弦节奏
```

**节奏本身产生周期峰，把真实延迟盖掉。**
**修法**：用**延音段**（无节奏）+ **波形相似性**（延迟重复是同一段波形副本，没有新起音瞬态）。

### ❌ 8.3 用传递函数相位/群延迟分析抓伪影

失真信号的相位行为会淹没 EQ 的相位效应（实测算出 70–80 ms 的群延迟σ，物理上不可能）。
**修法**：用**逐帧对齐的 lag**（整体延迟），它不受失真影响——实测干净地抓出了 FIX3 的 6.19 ms。

### ⚠️ 8.4 未决问题（已部分解答，2026-09-28）

**原问题**：FIX3 的"电音"到底是 EQ 的问题，还是**合成 DI × EQ 的交互**造成的？

**现在知道的部分**：

**① 内容不匹配确实会把误差放大 2–3 倍**
```
同一个预设 EQFIX2，同一个全曲目标：
  开放音阶 + C 和弦（内容不匹配）  →  3.87 dB
  E/B 强力和弦闷音（内容匹配）      →  1.60 dB
```
所以**"频谱指标和听感不一致"很可能有一部分就是内容不匹配造成的假误差**。

**② 合成 DI 会过拟合**
```
FIX4（用合成 F# 调 DI + 闷音窗目标调出来的）：
  训练场景（闷音）    改善 0.57 dB
  场景外（开放音阶）  变差 0.55–0.80 dB
```
**净负。** 用合成 DI 可以，但**目标必须是全曲**（§7.4），不能是闷音窗。

**③ 合成 DI = 管线验证夹具，不是音色参考**

它的价值是「让闭环在用户录音前就能跑起来」：验证发送 / 对齐 / 削顶 / 格式 / 解算 / 握手。
**它的误差推不出上界**（参考曲是湿声，结构不同，比不了）——
**推不出上界的误差不能进优化循环。**
用真 DI 定案时**必须回基准预设重新解算**（见 §9.1）。
**仍然未决**：FIX3 的"电音"到底是不是纯 EQ 问题。
**判定方法**（还没做）：把 EQFIX2 和 FIX3 用**同一个内容匹配的 DI** 各渲一遍，
对比逐帧指标（LSD / MCD / lag）。如果 FIX3 在这些指标上正常，
说明"电音"不是频谱层面的问题。

## 9. 标准工作流

**核心原则：先让目标和 DI 的内容对齐，再谈调参。内容不对齐，后面全是白干。**

```
┌─────────────────────────────────────────────────────────────┐
│ 第 0 步  分析参考曲（每首歌只做一次）                          │
│   分轨 → 吉他轨 → ① 全曲目标曲线  ② 演奏规格                  │
│   演奏规格 = 调性 / 主要和弦 / 奏法比例 / 音区 / 密度           │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ 第 1 步  准备内容匹配的 DI                                     │
│   主：用户按 di_instructions.py 的指令录（定 EQ 的唯一依据）     │
│   辅：合成 DI（gen_palm_di.py）—— 仅供参考，权重低               │
│   verify_di.py 自动检查：电平/调性/调弦/奏法                    │
│   ⚠️ 调性、奏法、和声必须对齐，否则后面测的都是假数字            │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ 第 2-5 步  调参循环（每轮一次 reamp）                          │
│   载入预设 → reamp → 测误差 → 解最小二乘 → 生成新预设           │
└─────────────────────────────────────────────────────────────┘
```

### 9.0 第 0 步：分析参考曲（产出目标 + 规格）

```powershell
# 新建一首歌的工作目录

### 9.1 第 1 步：内容匹配的 DI

**两条路。优先让用户录——这是最准的。**

#### 先测参考曲的奏法比例（§7.1 的描述子）

两个量：**低频段（100–450 Hz）占比** + **频谱重心**

```
参考基准（实测）:
  闷音          28.8%  /  1621 Hz
  开放弦        11.4%  /  2000 Hz
  泛音          基频被抑制，低频占比明显偏低
```

逐帧算这两个量 → 聚类 → 得到参考曲里各奏法的**占比**，写进 `spec.json`。

#### 让用户按规格录（唯一路径）

**先确认调弦——这一步必须问用户，不能只靠自动检测**

```powershell
tone.bat run check_tuning.py          # 自动判（仅供参考）
tone.bat run check_tuning.py drop_d   # 用户确认后手动设
```

**为什么必须问**：吉他和弦表在 Drop D / 标准 / 降半音下完全不同。
**实测**：按标准调弦算出的品数**全是错的**——用户弹的是 Drop D，
E5 是"6/5/4 弦全按第 2 品"（一根手指横按），不是"6 弦空弦 + 5 弦 2 品"。

**自动判据只有参考价值**：Drop D 的 6 弦是 D2（73.4 Hz），标准是 E2（82.4 Hz），
比 D2/E2 的出现率。**但吉他轨低音区有贝斯泄漏**（实测 61.7 Hz 的 B1 占 27%，
吉他根本弹不到那个音），所以自动判定会被污染。

**支持的调弦**（`di_instructions.py` 里）：`standard` / `drop_d` / `half_down` / `drop_c`

**强力和弦的按法规则（自动选最低把位）**：
```
Drop D 类：
  根音在 6 弦  →  6/5/4 弦【同一个品】，一根手指横按
  根音在 5 弦  →  5 弦 N 品 + 4 弦 N+2 品 + 3 弦 N+2 品
哪个把位低就用哪个
```

**给用户的指令：用脚本生成，不要手写**

```powershell
tone.bat run di_instructions.py
```

它读 `spec.json`（调性 / 和弦 / 奏法占比），输出**不含任何乐理词汇**的指令：

```
[调弦] Drop D (DADGBE)
==============================================================
   请录一段干声（吉他直接插声卡，中间不要接任何效果器）
==============================================================
总共约 26 秒，分三段。
★ 每段之间【完全停手 1 秒】——手离开琴弦，让声音彻底消失
  （系统靠这个静音自动分段，用来检查你每段弹对了没有）

第 1 段   闷音    约 16 秒
  第一个（弹这个最多）：
      . 第 6、5、4 弦【全部按第 2 品】
      . （一根手指横着压住这三根弦）
  第二个（隔一会儿换过去）：
      . 第 2 粗的弦（第 5 弦）第 2 品
      . 第 3 根弦（第 4 弦）第 4 品
      . 第 4 根弦（第 3 弦）第 4 品
  右手：手掌外侧【轻轻压在琴桥前面】，让声音变成短促的
        "哒哒哒"，不是"当当当"
        中速连续下拨，大约每秒 4 下

第 2 段   还是闷音，换个位置    约 7 秒
      G5：第 6、5、4 弦【全部按第 5 品】
第 3 段   放开手    约 3 秒
==============================================================
```

**段间必须"完全停手 1 秒"** —— `verify_di.py` 靠这个静音自动分段，
才能拿"用户的闷音段"跟"用户自己的开放段"对比（见下）。

**三条设计约束：**

| 约束 | 为什么 |
|---|---|
| **不给乐理词汇**（不写 "E5"、"根音"、"Ⅰ–Ⅴ"） | 用复制音色的多半是小白，写了他也不知道按哪 |
| **给弦号 + 品数**，0 品说"什么都不按" | 这是唯一不会歧义的表达 |
| **三段比例 = 测出来的奏法占比** | 分析结果直接变成"弹多久"，不是另写一套 |

**⚠️ MIDI 基准**：`C2 = 36`，`E2 = 40`。写成 `40 + index("E")` 会得到 G#2，
输出的品数全错（实测踩过）。

**录完之后：先验证，再归一化**

```powershell
$env:SONG_DIR = "<歌曲目录>"
# 录音放进 <歌曲目录>\di\，改名成 palm_di.wav

tone.bat run verify_di.py      # ★ 先验证
tone.bat run meas_prep.py      # 通过后再归一化
```

**`verify_di.py` 检查四件事**（不能退回合成了，那一次录音必须对）：

| 检查 | 判据 | 不对时怎么办 |
|---|---|---|
| **电平** | 不能是静音，不能爆音 | 提醒调声卡输入增益 |
| **时长** | ≥ 15 秒 | 提醒录完三段 |
| **调性** | 主音跟 spec 一致 | 报出实际主音 |
| **调弦** | 反推用户实际用的调弦 | 直接建议改成哪个，并重新出指法 |
| **奏法** | ★ **自参照**：闷音段的低频占比要比开放段高 ≥ 8 个百分点 | 提醒手掌要真正压住 |

**奏法为什么能自参照**：不跟任何绝对基准比，只比"用户自己的闷音段 vs 用户自己的开放段"。
**这样就不需要知道'真实闷音应该长什么样'**，只需要用户前后弹得不一样。

**⚠️ 不要盲减固定 dB**：真实录音的电平跟合成 DI 差很多。
`meas_prep.py` 用 `TARGET_PEAK`（默认 −32 dBFS）**自动归一化**——这个值跟历史所有测量一致。

#### 路径 B（辅助）：合成 DI —— **管线验证夹具，不是音色参考**

> **合成 DI 不是「差一点的 DI」，是「无法验证的 DI」。**
> **它的位置是夹具：证明链路通，不参与音色判定。**

**真正的理由（不依赖任何具体数字）**

```
想验证「这个 DI 弹得对不对」  →  只能跟另一个 DI 比
参考曲那边是【湿声】         →  频谱结构不同（失真堆谐波、混音又高通），比不了
⇒ 除了「用户再录一条」，没有任何办法判断合成 DI 偏了多少

推不出上界的误差  =  不能进优化循环
```

**「仅参考」的根据不是「它错得多」，而是「你无法知道它错了多少」。**
这个理由的好处：**不依赖具体测量值，换个合成算法也不会失效。**

（早先版本写的「低频占比 7.0% vs 97.1%、偏亮 14 倍」**已作废**：
那个对比把干声和湿声混在一起比，类别不同；绝对数值又依赖录音条件，复现不出来，
而且 7.0 / 97.1 这两个数出自已废弃的配方 A / D 两代实现（见 §7.2 的变体谱系）。
**能被后人当标定值引用的数字，必须站得住。**）

**它不可替代的用途：让闭环在用户还没录音时就能跑起来**

| 要验的 | 用合成 DI 能验吗 |
|---|---|
| 发送 PCM 相关性、削顶、对齐、往返延迟 | ✅ |
| 采样率陷阱（44100 / 48000）、`.mo` 格式校验 | ✅ |
| EQ 最小二乘解算、预设生成、握手流程 | ✅ |
| **音色对不对** | ❌ **只有真 DI 能验** |
| **预设之间的相对排序** | ✅ **见下** |

#### ★ 合成 DI 的第二个用途：相对比较（偏差会抵消）

```
输出 = DI 频谱 × 预设传递函数
        D(f)   ×     H_i(f)

比较两个预设：  D·H_i  vs  D·H_j
              比值 = H_i / H_j      ← D 被约掉了
```

**D 是所有预设共有的因子，在比值里自动抵消。**

所以分工是：

| 用途 | 用哪个 DI | 为什么 |
|---|---|---|
| **预设之间排序**（哪个更接近目标） | **合成 DI** | 偏差抵消；快，不麻烦用户 |
| **绝对匹配定案**（最终 EQ） | **真实 DI** | 偏差不抵消，必须用真的 |

> **这也是 §10.7 里「换箱头值不值得」那个实验能用合成 DI 跑的前提。**

**这些用任何 DI 都能验。** 等真 DI 到了，链路已经证明是通的——
**省下的是「在真 DI 上 debug 管线」的时间，那个代价高得多。**

**用它的正确姿势**

```powershell
tone.bat run gen_palm_di.py     # 按 spec.json 的调性生成
tone.bat run meas_prep.py
# ... 确认整条链路能跑通（发送 / 对齐 / 削顶 / 解算 / 生成 / 握手）
# 然后等真 DI 到了，回【基准预设】重新解算
```

#### ★ 用真 DI 定案时：必须回【基准预设】重新解算

**⚠️ 不要从「合成调出来的版本」继续迭代。**

原因：合成版里已经烘焙进了**「补偿合成器缺陷」的那部分 EQ**。
从它继续，那部分补偿会被当成「已经调好的音色」保留下来。

> **必须让最小二乘对真 DI 从零解一次。**

**配套要求**：`notes.md` / `spec.json` 里**逐轮记录「本轮基于哪个 DI」**。
否则三条 DI 混在一起调，回头没人说得清哪个预设是靠什么调出来的。
实测代价：

```
随便弹的开放音阶 + C 和弦     对目标偏差 3.87 dB    ← 60% 是内容差异
按规格弹的闷音（真 DI）       对目标偏差 1.60 dB
```

**内容不对齐时，你测的是内容差异，不是音色差异。而且你会照着这个假误差去调参。**
### 9.2 第 2-5 步：调参循环

```
② 测量        载入预设 → reamp → 得到湿声（先验证无削顶 + 发送 PCM 相关≈1.0）
③ 算误差      湿声的 13 频段包络 − 目标曲线      →  RMS 偏差
④ 解参数      用 EQ 响应模型做【最小二乘】解出各频段需要的单位数
⑤ 生成预设    用文本替换改 .mo（不要重新序列化 JSON，见 §3.3）
   回到 ②
```

**哨兵（每轮都要看）**：
```
削顶        >=0.999 的样本数必须为 0
参数步长    单轮 ≤ ±20 单位（§3.9）
对齐 lag    < 5 ms（异常说明群延迟变了）
MCD         相对基准 ≤ 2×
```

**收敛判定：看【单轮增益塌缩】，不看绝对阈值。**

实测轨迹：
```
总误差      3.53 → 1.60 → 1.51 → 1.49 dB
单轮增益           1.93   0.09   0.02      ← 这个才是信号
```
最终停在 **1.5 dB**，而这首歌的地板是 **2.01 dB**——**已经到地板以下了。**

> **⚠️ 绝对阈值（0.62 dB 量级）会一直给"还差得远"的错误信号。**
> 每个演奏者、每首歌、每套 DI 的地板都不一样。**先量地板，再看单轮增益。**
>
> **判据：单轮增益 < 0.1 dB → 这个维度榨干了，换维度或停。**

### 9.4 生成预设文件（.mo）的正确姿势

**不要用 `JSON.stringify` 重新序列化**——格式细节太多（§2.2、§3.3）。
**用文本定点替换**：

```javascript
const src = fs.readFileSync("EQFIX2.mo", "utf8");
const a = src.indexOf('"EQ": {');           // 只改这个块
const b = src.indexOf('"Switch"', a);
let block = src.slice(a, b);
for (const [k, v] of Object.entries(NEW_EQ))
  block = block.replace(new RegExp('("' + k + '":\\s*)(\\d+)'), `$1${v}`);
let out = src.slice(0, a) + block + src.slice(b);
out = out.replace('"name": "EQFIX2"', '"name": "FIX5"');   // 名字也换
fs.writeFileSync("FIX5.mo", out, "utf8");   // 不加 BOM，LF，结尾换行
```

**校验清单**（写完必查）：
```
Merge 长度 == 294
fileInfo.name <= 8 字符，纯字母数字
无 BOM / LF 换行 / 以换行结尾
JSON 可解析
跟源文件逐行 diff，应该只有你改的那几行不同
```

## 10. GE250 参数速查

### 10.1 EQ 模块（实测标定）

```
刻度      0 – 100
零点      50（= 0 dB）
量程      ±16 dB
单段增益  32 个单位 = 5.91 dB  →  每单位 0.185 dB
频段宽度  σ ≈ 1.0 倍频程（半高宽 2.32 倍频程）
频段      100Hz / 250Hz / 630Hz / 1.6KHz / 4KHz
换算      数值 = 50 + 目标dB ÷ 0.185
```

**注意**：五段重叠很宽，所以"频段中心处的提升"≠"单段增益"，是 2–3 段叠加。


#### ⭐ EQ 模型标定已验证（含频段重叠）

**两个常数**（多轮实测确认）：
```
1 单位 = 0.1848 dB        （50 = 0 dB，范围 ±16 dB）
σ = 0.985 个八度          （半功率宽度 2.32 个八度）
频段 100 / 250 / 630 / 1.6k / 4k Hz
```

**响应模型**：`gain(f) = Σ_b unit_b × 0.1848 × exp( −(log2(f/f_b))² / (2σ²) )`

**实测验证（FIX5 vs EQFIX2，同一 DI）**：

| 频段 | 施加(单位) | 实测变化(dB) | 模型预测(dB) | 差 |
|---|---|---|---|---|
| 268 Hz | +13 @250 | +1.57 | +2.22 | −0.66 |
| 380 Hz | +13 @250 | +1.59 | +1.96 | −0.37 |
| 3044 Hz | −11 @4k | −2.27 | −2.14 | −0.13 |
| 4305 Hz | −11 @4k | −2.59 | −2.19 | −0.40 |

**模型误差 RMS 0.43 dB，最大 0.66 dB → 可信。**

#### ⚠️ 频段重叠：必须用最小二乘，不能朴素换算

**同一个误差向量，两种算法的结果差很多：**

```
误差: 190Hz −2.21, 268Hz −1.31, 380Hz −2.33, 4305Hz +2.52, 6088Hz +2.31

朴素换算（每个频段独立）:  100Hz +8, 250Hz +12, 630Hz +6, 1.6k −6, 4k −10
最小二乘（考虑重叠）:      100Hz −3, 250Hz +13, 630Hz +1, 1.6k −2, 4k −11
                                  ↑差 11 单位          ↑差 5 单位
```

**原因**：250 Hz 那个 +13 单位，靠 ±1 个八度的带宽已经覆盖了 134–380 Hz，**再动 100 Hz 就过头了**。630 Hz 同理被 250 和 1.6k 夹住。

**照朴素值调会过冲。必须解最小二乘。**

### 10.4 ⚠️ 界面显示的 dB 是 UI 假象（差约 3 倍）★

**GE250 Edit 界面上那排 dB 数字不要拿来算参数。**

```
界面规律:  dB = 数值/2 − 16        （超出 ±16 截顶）
  100Hz=30  →  界面 −1.0
  630Hz=69  →  界面 16.0（真实 18.5，被截顶）
  4KHz=61   →  界面 14.5

真实刻度（界面背后的实际刻度）:
  0.1705 dB/单位，σ = 1.030 八度      （閃光会话独立标定）
  0.1848 dB/单位，σ = 0.985  八度      （本文档 §10.1，BlackShout 会话标定）
```

> **两个标定差 8%，都在同一量级。以 §10.1 的 0.1848 / 0.985 为准**
> （它有 §10.1 的逐点验证，模型误差实测 0.43 dB RMS）。
> 另一个标定的价值是**证明这个刻度跨会话可复现**，不是取代它。

**踩的坑**：看到预设里 `EQ 全 100`、界面显示 `+16.0 dB`，误判成"EQ 被炸了"，
**白跑一整轮**。实际 100 对应的是 +8.5 dB 左右，不是 +16。

> **写死一句：界面上那排数字只用来确认"大概在哪个位置"，不要用来算参数。**

### 10.5 ⚠️ AMP `Mst` 是【线性幅度】控制，不是 dB 控制

```
Mst 55 → 35    实测 −3.15 dB    20·log₁₀(35/55) = −3.92 dB
Mst 35 → 15    实测 −7.02 dB    20·log₁₀(15/35) = −7.37 dB
```

**同样 20 个单位，在不同位置降的 dB 完全不同** ——
**不存在固定的 dB/单位。**

**换算公式**：`ΔdB = 20·log₁₀(新值 / 旧值)`

**适用范围**：音量类参数都这样——`Mst` / `Drive` / `Volume` / `Level`。
**只有 EQ 是 dB 刻度**（1 单位 = 0.1848 dB）。

### 10.6 ⚠️ 整条链的输出恒定贴着 0 dBFS，而且会靠饱和"补"高频

**输出峰值跟发送电平几乎无关**（实测）：

| 发送 | 输出峰值 | 输出 RMS | 削顶样本 |
|---|---|---|---|
| −32 dBFS | **0.00 dBFS** | −13.18 dBFS | **13 个** |
| −38 dBFS | −0.02 dBFS | −14.96 dBFS | 0 个 |

**发送降 6 dB，输出峰值纹丝不动。**

#### 后果一：削顶是常态，不是例外

**输出峰值必须 < −0.1 dBFS。贴着 0.00 本身就是警报——削顶数为 0 只是运气。**
（见 §6.4 哨兵表）

#### 后果二（重要）：输出级在饱和，而饱和会往 6 kHz 补内容

波峰因数（峰值 − RMS）：
```
Mst = 35    14.9 dB    ← 饱和中
Mst = 15    20.7 dB    ← 干净
歌曲吉他轨   17.4 dB    ← 参考
```

**Mst=15 干净之后，6088 Hz 掉了 3.56 dB，误差从 1.52 涨到 1.89。**

> **含义：如果匹配点落在"输出级刚好饱和"上，那个匹配是【脆】的。**
> 它确实测出来更好，但要知道自己是在**靠饱和补高频**——
> 换个演奏力度、换个发送电平，那个补偿就没了。

**行动**：调到一个"不靠饱和"的工作点，再看误差。
如果误差明显变大，说明之前的匹配有一部分是假的。

### 10.7 箱头 / 箱体 / 推子的选择 —— 经典配置（★ 补的是音色的另一半）

> **本文档 §1–§9 全在讲 EQ。但音色有一半由箱头/箱体/推子决定，EQ 只能在这一半之内修。**
> **这一节讲那一半怎么选。**

#### 10.7.1 结论：这半件事靠【经典配置】，不靠搜索

**吉他界几十年的共识就是一张对照表。人也是这么做的：**

```
经典解起手（例：摇滚 = TS808 + JCM900）
  →  靠耳朵微调
  →  调不动了就停
```

**本 Skill 走的是同一条路，只是把「靠耳朵微调」换成了「最小二乘解 + 单轮增益判据」。**
**价值不是比人调得好，是不依赖操作者的经验年限，且结果可复现。**

**⚠️ 不要试图暴力搜索箱头**：GE250 有 **165 个箱头 × 190 个箱体**，
而且换预设必须**手动加载**（实测 USB **不暴露 MIDI 端口**：
`midiOutGetNumDevs()` = 1，那还是系统自带的波表合成器，不是 GE250）。

#### 10.7.2 MNRS 采集分两类（决定链路上要不要开箱体模拟）

| 类型 | 含义 | 链路 |
|---|---|---|
| **Entire 采集** | 箱头 + 箱体 **一体** | 加载后 **不要开 CAB 模块** |
| **Preamp 采集** | 只有前级 | **必须**配 CAB 模块 |

**优先用 Entire**：一次只选一样东西，不会出现「箱头没选错但箱体把它掩盖了」。

> GE300 用户注意：用 Entire 时要在 AMP 模块里**关掉后级模拟**（GE250 无此问题）。

#### 10.7.3 经典配置对照表（从 GE250 实际有的清单里选）

| 音色 | 箱头 | 箱体（若用 Preamp） | 推子 |
|---|---|---|---|
| **摇滚 / 硬摇滚通用** | MARSHALL JCM900 · JCM800 | 4x12 G12T-75 | **TS808 / SD-1** |
| **日系摇滚 / anisong** | MESA MARK V · JP2C · DUAL RECTIFIER | 4x12 V30 | OD（Gain 低 / Level 高） |

#### 10.7.4 推子的通用用法（跟箱头同样重要）

```
TS808 / OD808 / SD-1 类：
    Gain  → 0 ~ 低     不加失真，只做过载
    Level → 高          推前级
    Tone  → 中位

效果 = 切低频 + 抬中频  →  让高增益箱头变紧，riff 更清晰
```

**这就是为什么高增益音色几乎都带一个 OD** —— 不是为了加失真，是为了**塑形**。

#### 10.7.5 怎么判断该不该换箱头（唯一硬判据）

> **不问「哪个听着像」，问「哪个在 EQ 优化完之后残差更低」。**

```
EQ 只能改频谱包络。
某个组合在 EQ 拉满后残差仍然大
  →  它的【谐波生成结构】跟目标不对
  →  那正是箱头/箱体的本质区别，EQ 修不了
```

**因为 §10.1 有已验证的 EQ 响应模型（0.43 dB RMS），所以能【软件里预测】最优 EQ 和残差**
—— 每个候选只要 **加载 1 次 + reamp 1 次**，不用真的迭代两轮。

#### 10.7.6 什么时候可以【忽略】这一维

**三条同时成立就该停：**

| 判据 | 实测 |
|---|---|
| **当前残差已到/低于地板** | 閃光：残差 1.49 dB，地板 2.01 dB → 已在地板以下 |
| **地板主要压在低频段**（那是源差异，不是箱头） | 地板主导频段 134/190/268/537/1522/2152 Hz |
| **可能的提升小于听阈** | 人耳阈值实测 ≈0.5 dB（1.77→1.23 用户听不出） |

**参考量级**：箱头模块的贡献约 **1.7 dB**（实测：空音色 3.51 dB → J900R 1.77 dB）。

> **所以：如果换箱头最多只能挤出 0.5 dB 以内，而地板主要在低频 —— 换它没有意义。**
> **这时候正确的做法是停，不是继续。**

> **比对要成立，内容和目标必须先对齐——奏法、调性、和声、调弦缺一不可。**
> **内容不对齐时，测出的「音色误差」里有 60% 是假的。**
> **每次测量前验证发送信号与削顶；小步迭代；误差分地板和可行动；**

### 收敛与验证

## 13. 扒谱 / 分析参考曲的边界（实测）

**目标不是"能照着弹的谱"，是"能弹出一段内容匹配的 DI"。** 两者难度差很远。
13. **描述子/指标必须钉死在代码里**（`songlib.technique_descriptor`），
    文档只指向代码。**同一份实现重写一遍就会漂 1.1~1.7 倍**（§7.2）
13. **配方里每留一个没写明的自由度，就等于给未来的自己埋一次 1.6 倍**
    已知自由度：域（比值/质心可不同域）· 统计量 · 门限 · 频段 · 分母上限 · 窗长 · hop
    **锚点必须带实现版本号**，否则后人无法判断它还有没有效

### 13.1 可靠的

| 项 | 方法 | 实测结果 |
|---|---|---|
| 起音密度 | 自适应阈值谱通量 | 某首 4 分钟曲：2558 个，密集段 10–14 音/秒 |
| 调性 | chroma 汇总 | 主音占比 44%、属音 19% → 判定明确 |
| （前置守卫） | **先看平坦度 `max/mean`** | **实测某首曲只 1.23 → 被抹平了，那份结果是垃圾** |
| 和弦（按乐句） | 逐乐句 chroma + 模板匹配 | 可行，见下 |
| 音区 | 逐音 f0 的中位/分布 | 低把位为主 |

**⚠️ 用"全曲平均 chroma"之前，先看平坦度 `max/mean`。**
实测有一首曲子的平坦度只有 **1.23**——真实音乐不可能这么平，
**说明 12 个音级被抹平了，那份结论无效**。
**判据：< 1.5 就按半小节分段再看**（这是 §13.3 的前置检查）。

### 13.2 不可靠的

**① 逐音扒谱（密集失真 riff 上不可行）**
```
12.9 音/秒 → 每个"音"只有 58 ms
8192 点分析窗 = 186 ms，窗比音还长
→ f0 乱跳（实测 E3/G#2/G2/D2/F2/C3 之间跳）
```
**而且 12.9 音/秒根本不是"一个个音"，是连续击弦。**

**② HPS 的八度错误**
失真信号基本音弱、二次谐波强，谐波积谱会锁到 H2 上。
```
实测：E2（82.4 Hz）被报成 E3（164.7 Hz）——正好是 2 倍
```
**修法**：HPS 之后做次谐波校验——如果 f0/2 的谐波支撑度差不多，说明真基频更低。

**③ 失真强力和弦的大小调判定**
```
chroma 里根音和五度最强，三度音经常被谐波掩盖
实测：66% 判成"大三"，但失真吉他里大部分其实是【没有三度的强力和弦】
→ 这个比例不能当真
```

### 13.3 正确做法：按乐句算和弦

```python
# 逐【半小节】或【1-2 秒】算 chroma，再跟和弦模板余弦匹配
c = librosa.feature.chroma_cqt(y=seg, sr=SR, hop_length=512)
v = c.mean(1); v = v / v.sum()
# 模板：强力和弦(根+五) / 大三(根+五+大三度) / 小三(根+五+小三度)
```

**输出**：和弦进行（去重压缩后看变化点）。

**速度检测要留个心眼**：`librosa.beat.beat_track` 常给出实际值的一半
（实测给 92.3 BPM，实际可能是 184.6）。**这只影响乐句切分的粒度，不影响调性。**

### 13.4 对 DI 指令够用了

```
知道调性 + 主要和弦 + 调弦 + 奏法  →  就能生成"让用户弹什么"的指令
不需要音高、不需要节奏型、不需要指法
```

**实测验证**：照这个粒度生成的指令，用户能照做（见 §9.1）。

> **⚠️ 这里的"够用"指的是【生成给用户的指令】够用，
> 不是指合成 DI 够用** —— 合成 DI 已降级为"仅参考"（见 §7.5 / §8.4③）。
